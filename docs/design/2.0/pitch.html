Pitch for review · 2026-11-14

ThunderClap as the foundation for every game we make

Forge Wilds is the first large game it has to support. Prepared by the PM for both projects.

The pitch. ThunderClap stops being a rendering framework that games bolt their own foundations onto, and becomes the foundation itself: rendering, worlds, characters, UI, input, VR, quality control, and the client–server seam. Every game, from a 2D puzzler to a voxel world in a headset, then writes only its rules, content and art. Forge Wilds is the proof at scale: about half of its client is already foundation code, and that code is better than what ThunderClap has today, so it moves into the engine, generalized, rather than being rebuilt.

Why now

  • We are building the same foundations twice. Forge Wilds' client is 107k lines. About 60k of it is general-purpose: terrain streaming and meshing, procedural models, GPU-posed characters, one HUD for screen and headset, VR, quality tiers. ThunderClap is 9 days old and already has simpler versions of most of it.
  • Each half is strong where the other is weak. Forge has the scale engineering: a GPU-driven renderer that draws any amount of terrain in a fixed 46 GPU calls, an 8-byte vertex, tested on the iPad. ThunderClap has the breadth: 2D, glTF characters, a full post stack, shadows, GPU particles, sound, every page host, a clean module boundary and a release process.
  • Neither is the foundation alone. I measured ThunderClap drawing our real world on the iPad profile: 2.5× the CPU and 1.8× the GPU of today's client, and its voxel module can't hold our world. Forge's renderer, meanwhile, knows nothing about 2D, glTF or other games.
  • The engine was designed before it knew about networked games. Its rules make netcode, servers and world streaming "the game's job". A foundation for games at Forge's scale has to own the seam between client and server.

What the engine becomes

One renderer in two layers, a kit of modules a game picks from, and a game layer that holds only what makes that game itself.

Each game: rules, content, art direction (its shaders), scenes, its server's rules. Forge Wilds keeps about 50k lines: net and play, panels, the world's look, its content adapters.
Foundation modules (new or rebuilt from Forge): streamed voxel worlds · procedural part models · GPU-posed characters (rigid or glTF-skinned) · UI described once, shown on screen and in a headset · input as intents, aimed by a ray · quality tiers and a load governor · the client side of networking
Existing ThunderClap modules, kept: 2D kit · glTF and animation · post stack · particles, sky, water, decals · audio · hosts (web, Electron, Capacitor, PWA) · saves · i18n
Render core (rebuilt): a retained, GPU-driven core that does the work once for every view (two eyes in VR cost one cull), with ThunderClap's simple per-frame calls on top so a 2D game never pays for it
Rails: counted-work tests, WebKit iPad as the reference device, a stereo path, reference scenes for 2D, 3D characters, voxel worlds and VR

What doesn't change in ThunderClap's vision: no game nouns, games import the engine and never the reverse, no runtime dependencies, WebGPU and WebXR only, shader-first with asset files optional, one engine for 2D and 3D, and the goal of shipping a game in two weeks to a month. The Last Rune keeps its source and stays pixel-identical.

The decisions I need from you

Three. Each has my recommendation; a word is enough.

1. Change ThunderClap's rule 5 from “rendering, not mechanics” to “foundations, not rules”

Rule 5 today says a voxel mesher, a pathfinder or netcode is each game's own pipeline, “even when two games share it”. That rule blocks the whole pitch: under it, Forge keeps its world, models and characters, and the next game at its scale copies them.

The new rule: anything every game of a kind would otherwise rebuild (world storage and streaming, meshing, light, characters, UI, the client side of networking) belongs in the engine. Rules, content, AI, world generation and art stay each game's. Rule 1 (no game nouns) still guards it: a module joins only when its API names nothing from any game.

Recommendation: yes. It is the change that makes “the foundation for dozens of games” true.

2. Does ThunderClap own the server side too?

Forge's strongest asset is its Rust server: an event-sourced, deterministic world with a scheduler, live areas, persistence, a generated protocol and an SDK that bots play through. Today none of that is ThunderClap's.

OptionWhat it means
A. Client side onlyThunderClap gains a networking client module (sessions over a transport the host supplies, snapshot buffers, interpolation, prediction and rollback, interest). Every game still writes its own server.
B. Both sides, client firstA, then a sibling thunderclap-server made from Forge's Rust engine with the game taken out (log, scheduler, live areas, persistence, protocol generation, bot SDK). A game writes its rules; the engine runs them, saves them and streams them.
C. A TypeScript serverA Node server that shares code with the client. Simpler for small games, but it throws away the Rust engine Forge spent 12 hardening rounds on.
Recommendation: B. Build the client side in this program. Research the server half now, in parallel, and build it once the client foundation has proved itself. The engine still never opens a connection on its own: the host hands it one.

3. When does Forge Wilds switch a module over?

You said the engine's performance can be tuned over time, and the vision must not be compromised. Forge's standing rule has been that no change may cost the iPad frame time. These pull against each other at the moment Forge switches a module to the engine.

OptionWhat it means
Strict parityA module switches only when it costs nothing: counted work (GPU calls, allocations, bytes) equal or lower and measured CPU and GPU time within the day's noise. Safest for players; the program goes as slowly as the slowest module's tuning.
Hard on design, soft on timingCounted work, bundle size and memory stay hard limits, because they prove the architecture is right. Measured time may be somewhat worse at the switch, as long as the iPad still holds a steady 60 fps (GPU p95 ≤ 10 ms) with no new hitches. The time gap is logged as debt with an owner and closed by tuning.
Recommendation: hard on design, soft on timing. It matches what you said: the foundation must be trustworthy (counted work can't regress, so nothing is built the slow way) while raw speed is tuned over time. The full gate is in “The speed bar” below.

Calls I've made (tell me if you disagree)

  • VR is first-class in the engine from day one. Every render-core change is tested with two views on a simulated headset. Forge's own headset work stays shelved until you lift it.
  • The Last Rune stays pixel-identical through the rewrite; only a bug fix you approve changes its look.
  • Forge's game work continues only where nothing is moving. Rules, content, the server and game UI words can keep going. The client's foundations (render, mesh, actors, UI framework, XR) are frozen except for fixes while they move.
  • I run both repos as one program. ThunderClap work follows its own PM rules (branches, integrators, its gate); Forge follows its PR flow. I own both roadmaps for this program.
  • Pace: 6 to 8 top-level agents across both repos, at most about 6 of them doing heavy builds at once. Raise or lower it as you like.

How we'll know it worked

  • Forge Wilds runs entirely on ThunderClap at or above the iPad floor, and its client shrinks from 107k to about 50k lines of game code.
  • The Last Rune is pixel-identical and its bundle no larger.
  • A new game reaches playable in two weeks with nothing in its repo but rules, content, scenes, shaders and a createGame() call.
  • VR works for every game through the same path, tested on every core change.

The biggest risks

  • Generalizing costs speed. Forge's terrain shader is 6–7 ms of an 8 ms iPad frame. Mitigation: the engine generates the vertex decode at build time and it must match today's shader token for token.
  • ThunderClap is young and has never run on WebKit. Mitigation: WebKit and iPad rails come first, in phase 0, before any code moves.
  • Two repos, one cadence. Mitigation: a next release channel and a local link, so Forge never waits on a publish.
  • Bundle size. Forge has about 30 KB of room. Mitigation: the kit split, and every module Forge adopts deletes at least its own size from Forge in the same PR.

The architecture's ten principles
  1. One renderer, two layers. A retained, GPU-driven core (buffer arenas, GPU culling, render bundles of indirect draws) under ThunderClap's immediate calls (frame.sprite, frame.mesh, InstanceList). A 50-sprite puzzle pays one upload and one sorted list; a voxel world pays only for what changed. Rejected: separate 2D and 3D renderers (two post, XR and test stacks); GPU-driven for everything (no gain for small games, harder to debug).
  2. Views are plural from the bottom. Prepare once, draw each view. A stereo pair is one cull group. Rejected: render per eye, as ThunderClap does today.
  3. Pay only for what is used. Passes, targets and attachments exist only when something records into them. The always-on emissive target is the spike's main GPU-cost suspect.
  4. Kit, not framework. createGame composes services the game imports; nothing is mandatory. On/off flags alone still pull in all the code (169 KB gzip).
  5. Data in, no scene graph. The game owns state; the engine owns buffers.
  6. Shader-first, asset-optional. Games write WGSL; procedural geometry is first-class; glTF is an opt-in island. No WGSL override (the iPad's WebKit needs this).
  7. UI described once as data. Presenters per surface (screen and in-world); the look is tokens, not parsed CSS.
  8. Input as actions, then intents; aim is always a ray.
  9. Counted work is the engine's product. The WebKit iPad is the reference device; tests count GPU calls and allocations, since a shared machine can't gate wall time.
  10. Generalize, never copy. Forge code moves only once its game nouns are declared data (for example, a vertex bitfield schema that generates the shader's decode).

ThunderClap's own rails (phase 0): a WebKit test project, a counted-work budget framework (~1k lines), bench rungs for 2D, a skinned crowd of 64, a streamed voxel world and stereo, bundle budgets per module, a tree-shaking check, 3D golden images. Six reference scenes: 2D (The Last Rune), characters, a lit arena, a voxel world, VR stereo, an idle HUD.

New findings while setting the bar: ThunderClap already allocates nothing and reads no clock per frame. It fails on GPU calls, which grow with what's visible (1,366 at 1,500 meshes, 5,358 at 6,000, doubled for two eyes) against Forge's flat 46. It ran in WebKit for the first time with no errors. WebKit's clock only resolves to 1 ms, so CPU times must be batch totals; the spike's 1.0 ms reading for Forge has the same flaw, and the terrain GPU gap (2.9 vs 5.1 ms) must be re-measured back to back before any terrain decision.

The render core, in more depth
  • Draw sets. Every draw lands in a set: a pipeline, an instance layout, a source of instances, a cull mode. Static sets live in render bundles; dynamic sets upload only dirty ranges; large sets are GPU-culled. The immediate API fills one transient set per material and mesh each frame.
  • Arenas and layouts. Shared vertex and index arenas, custom vertex and instance layouts (packed integers allowed), one shared quad index buffer.
  • Indirect drawing. Bundles of indirect draws are the baseline because WebKit lacks multi-draw; multi-draw is used only where the device has it.
  • Passes. Named passes; drawables can be opaque, cast shadows and receive each view's camera. A declared pass list, not a frame graph, until a third game needs more.
  • Stereo once. One cull, one upload and one shadow pass for both eyes.
  • Camera-relative origin so large worlds keep precision.
  • The Last Rune's guarantees: source-compatible (its imports checked as an allow-list), all 86 screenshots pixel-identical, a call-trace diff against 1.3, bundle at most +2 KB.
