# ThunderClap engine: architecture and contracts

`@thunderclap/engine` is the WebGPU engine The Last Rune is built on. It knows nothing about any game. This file is the target the PM reviews promotions and public API changes against (D-041, [refactor plan](https://github.com/Mandalorian007/last-rune/blob/main/docs/engine/refactor-plan.md)). Decision numbers (D-0xx) and `docs/` paths in this repo refer to [The Last Rune](https://github.com/Mandalorian007/last-rune), where the engine was built. Each contract says what exists **today** (0.2.0-dev) and what is **planned**, with the phase that delivers it.

## Package shape

```
thunderclap-engine/
  package.json        # @thunderclap/engine; the "exports" map is the public API
  pnpm-workspace.yaml # packages: ['packages/*']; the engine stays the root package
  packages/
    host-electron/    # @thunderclap/host-electron: the Electron shell (main, preload) and
                      # createElectronHost(); depends on the engine via "workspace:*" (links the root)
  src/
    index.ts          # the "." entry: createGame and its types
    audio/  core/  fx/  host/  input/  platform/  post/  render/  save/  ui/
  harness/            # noun-free e2e pages: index.html boots the platform layer (window.__harness);
                      # game.html boots through createGame (window.__harnessGame); ui.html is DOM only
  e2e/                # engine e2e specs, fixtures, ports, itch-style iframe wrapper
  playwright.config.ts  # the viewport/device/wrapper matrix every engine spec runs on
  ARCHITECTURE.md     # this file
  CHANGELOG.md
```

**Test ownership (D-041 addendum 2).** The engine verifies platform capability once, for every game: unit tests (`src/**/*.test.ts`, Vitest) and e2e specs (`e2e/`, Playwright) run against the `harness/` page. Every spec runs on the whole matrix in `playwright.config.ts`: desktop 1280×720 and 1920×1080, iPad 1180×820, four phones (667×320, 844×340, 932×380, 915×360, touch at DPR 2), and the harness inside an itch-style cross-origin iframe. Two upright rows, `phone-port` 390×844 and `tablet-port` 820×1180, run the layout spec only. A new platform capability (host, gestures, layout, lifecycle) adds a probe to the harness and a spec here, not in a game. Games test product only.

Games import only the exports map: `@thunderclap/engine` (the `"."` entry: `createGame` and its types) and `@thunderclap/engine/<module>` for `audio`, `core`, `fx`, `host`, `input`, `platform`, `post`, `render`, `save` and `ui`, plus `@thunderclap/engine/testing` (the recording fake `GPUDevice`, for unit tests only). Each subpath is that module's `index.ts`; anything not re-exported there is internal. `pnpm check:boundaries` (`scripts/check-boundaries.mjs`, part of `pnpm check`) fails if anything under `src/` imports from outside `src/` or through the package name, or if `harness/`, `e2e/`, `examples/` or `templates/` imports a subpath outside the map or reaches into `src/` by a relative path. Inside the package, modules import each other by relative path. A game, in its own repo, is held to the same map by its own checks.

**Workspace.** The engine is the root package, so a dependency on this repo by URL still resolves to it. `packages/host-electron` is a workspace package that depends on the engine with `"workspace:*"`, which pnpm links to the root. It is self-contained: the root `tsconfig.json` does not include `packages/`, and `pnpm check` runs `check:host-electron` (typecheck, lint, unit tests) after the engine's own checks. Desktop builds go to `dist/desktop/` at the repo root (gitignored). The engine never imports the package.

The package ships TypeScript source; the game's Vite build compiles it. There is no separate engine build until Phase 5 (extraction and publishing).

## Ground rules

1. **Promotion rule.** Code enters the engine only if Last Rune uses it, the next game plausibly would, and its API has zero game nouns.
2. **Dependency direction.** `games/*` imports `@thunderclap/engine`; the engine never imports a game. A game's `rules/` imports nothing from the engine or the DOM.
3. **No runtime dependencies** without a DECISIONS entry (D-008). WebGPU is the only renderer.
4. **Seams, not features.** 3D content and XR are out of scope until after Gate 5. The engine grows the three seams they would plug into (`Surface`, `Camera`, the frame loop) and nothing else on speculation.

## Contracts

**Surface.** Owns the canvas, the swapchain, DPR, the backbuffer size and the letterbox or fill-width fit. It exposes `rect` (CSS px), `size` (device px), `clientToLogical` and `onResize`. Later an `XRSurface` provides a target per eye per frame through the same interface. *Today:* `Surface` / `mountSurface` in `platform/surface.ts` exposes `rect`, `backbuffer` (device px; the planned name is `size`), `clientToLogical`, `logicalToClient`, `onResize`, `setFill` (fill-width) and `setFrame(rect | null)` (letterbox inside a part of the container, CSS px, e.g. the layout's `freeRect`), over the pure letterbox math in `platform/letterbox.ts`; `initGpu` configures the swapchain. *Planned:* the `size` rename and the target-per-frame shape arrive with Phase 3's `render(camera, target)`; `XRSurface` is after Gate 5.

**Camera.** A view-projection matrix plus `worldToScreen` and `screenToWorld` (the inverse projection; touch aiming uses it). Presets: `ortho2d(designW, designH)`, where 1 unit = 1 design px, and `fitRect(rect, viewport)`, which fits a world rect into a viewport. Depth test and depth write are camera-preset flags; the 2D preset leaves both off. *Today:* `render/renderer.ts` has a 2D `Camera` (`x`, `y`, `zoom`, `rotation` over the logical space) read from `renderer.camera`; draw order is submission order with no depth. *Planned:* Phase 3 (ws/camera) adds the matrix `Camera`, `mat4` in `core/math.ts` and the camera uniform block.

**Frame loop.** `GameLoop` as today (fixed 60 Hz update, variable render), but `render(camera, target, alpha)` takes the camera and the target as inputs instead of reading them from the renderer. The host decides who schedules frames (rAF, Electron, later `XRSession.requestAnimationFrame`). *Today:* `GameLoop` and `FixedStepper` in `core/loop.ts` (fixed step, `maxFps` cap, pause) call `render(alpha, time)` from `requestAnimationFrame`. With `GameLoopOptions.fixed: false` (what `createGame({ sim: false })` uses) there is no accumulator: `update(dt, time)` runs once per rendered frame with the real clamped delta, `render` gets `alpha` 1, and pause still skips update; `Scene<Ctx, Frame>` and `SceneStack` in `core/scene.ts`. *Planned:* the `render(camera, target, alpha)` signature in Phase 3 (ws/render-call); host-owned scheduling with the host layer.

**Host.** `interface Host { kind; openExternal; copyText; fullscreen; storage; window?; embed }`. Implementations: `web` (detects iframe vs top and wraps today's D-036 link service) and `electron` (preload bridge). After Phase 1 the engine never calls `window.open`, `navigator.clipboard` or `localStorage` directly. *Today:* `host/` (`@thunderclap/engine/host`) has the `Host` type, `createWebHost({ win? })` and `defaultHost()` / `setDefaultHost()`. The web host also exposes `clipboardWriteAllowed()`; `fullscreen` is `{ available, active, toggle, watch }` and `storage` is `{ kind, open(): StorageLike | null }`. `save` (`createSaveStore`, `listSlots`), `persistMixer` and the `externalLink` widget take `host` and default to `defaultHost()`. `window.open`, `navigator.clipboard`, `execCommand` and `localStorage` appear only in `host/web.ts` and `host/web-links.ts`; the fullscreen DOM calls stay in `platform/device.ts`, which the web host wraps. The Electron host lives in this repo as `packages/host-electron` and provides `createElectronHost()` (`@thunderclap/host-electron`): the same interface over the preload bridge `window.thunderclap`, `kind: 'electron'`, storage the renderer's `localStorage` (served from the fixed origin `app://bundle`), and `window` with `close`, `minimize`, `toggleMaximize` and `setTitle`. A game installs it with `setDefaultHost` or passes it to its ctx; the engine never imports it. *Planned:* `Host.requestFrame` (rAF on web and Electron, `XRSession.requestAnimationFrame` later), so XR is a `Host` implementation, not a redesign; `GameLoop` takes its frame source from it (ws/render-call, D-044).

**Input.** The action map for keyboard, mouse, touch, pen and gamepad, with `blocked()`, `lastDevice`, queued taps, iframe-safe `preventDefault`, injectable pads and public feed methods for tests; `ui/padnav.ts` drives modal panels from the pad and `ui/menu-nav.ts` (`menuNav`) drives non-modal menus. `Gestures` (`input/gestures.ts`) recognises tap, double tap, long-press (450 ms), pan, drag (with its origin) and pinch (scale) from pointer events, with thresholds in CSS px (pan 10) and positions in game space through the same `PointerTransform`. It reports per tick like `Input`: one discrete gesture per kind per tick (extras queue), continuous ones every tick from `start` to `end` or `cancel`. `input.setGestures(g)` links it: the gestures share `blocked()` and the transform, attach with `Input.attach`, advance in `Input.update()`, and can be bound as actions (`{ gesture: 'tap' | 'doubleTap' | 'longPress' | 'pan' | 'drag' | 'pinch' }`), so a game can map tap to `select` and long-press to `info` without reading gestures. While blocked nothing is reported and a running pan, drag or pinch gets one `cancel`. The `magnify` option (`input/magnify.ts`, ws/port-altar) is loupe and snap for small touch targets: while one touch pointer is down each tick reports `gestures.aim`, the finger raised by `lift` (56 CSS px) while it drags, snapped by the game's `snap(x, y)` (usually `snapToGrid`, the nearest accepted cell within half a pitch), and while `pitch()` is below `below` (44 CSS px) a `Loupe` beside the finger magnifies the aim point `zoom` (2.5) times with the target ringed. The aim the finger lifted at is reported once more (`ended`) on the drag's `end` tick, so a dragged thing lands where it was aimed. Mouse and pen never aim. The loupe and its leader line (dense-board-4) are `position: fixed` elements in client px outside the overlay's layers, so overlay units never apply to them.

**Layout.** One overlay, laid out in CSS px on every form factor (ws/one-overlay, D-044). A `LayoutSpec` names regions (`top`, `left`, `right`, `bottom`, `cardLane`, `captionLane`, `modal`) per form factor (`phone`, `tablet`, `desktop`, each in `landscape` or `portrait`), with safe areas. Games register widgets against regions and the engine places them with CSS grid. The layout reports the free rect, so the world can frame into what the UI leaves. Density tokens `--tc-text-min`, `--tc-tap-min` and `--tc-text-scale` replace the game's `--lr-*` variables. *Today:* `createOverlay` in `ui/overlay.ts` builds one `.tc-overlay` root over the whole parent (letterbox bars included), with no transform, and its layout (`overlay.layout`; `ctx.ui.layout` in a game). Layers, bottom to top: `hud` and `captions` sit on the **frame** (the canvas rect, `--tc-frame-x/y/w/h`, set by `setFrame` on every resize) and clip to it; `layout` covers the whole root; `panels` and `toasts` sit on the frame in `frame` units and cover the root in `css` units. Each form's `FormSpec.units` picks the units (`data-units` on the root, `overlay.units`): `frame` (desktop, tablet) sizes the base UI in design px of the 1920×1080 frame, `--tc-dpx` CSS px each, so it keeps its proportions to the canvas; `css` (phones) takes `cssPxTheme` sizes as CSS px. `--tc-unit` is what one px of a design-px stylesheet draws as on each layer: `--tc-dpx` on the frame's layers, 1px in the regions and, in `css` units, in panels and toasts. `toFrameUnits(css)` (in `ui/text-scale.ts`) rewrites a design-px sheet's `Npx` to `calc(N * var(--tc-unit, 1px))`; games pass their sheets through it and `scaleFontSizes`. World-anchored DOM (labels over 3D objects) goes in `hud` at its design coordinates times `--tc-unit` (the same point as `surface.logicalToClient`), so it follows every resize without JS. Native controls whose parts are CSS px (range thumbs, select arrows) are zoomed by `--tc-zoom` (the scale as a number) on the frame's layers. `createLayout(overlay, spec?)` in `ui/layout.ts` classifies the form factor (`phone-landscape`, `phone-portrait`, `tablet`, `desktop`: a phone is a coarse pointer with a short side of at most 600, or any view under 480), resolves each form's px tracks and grid areas inside the safe area (`env(safe-area-inset-*)`, overridable with `--tc-safe-*` or `setSafeArea`), collapses tracks whose regions have no widgets, and draws the same px grid in the DOM. `layout.add(el, { place: { default, <formFactor> } })` moves a widget between regions on an orientation change; `'hidden'` hides it; `{ region: 'free', rect, reason }` is the escape hatch (logged once with `console.info` and listed in `freeUses`); `WidgetHandle.remove()` puts an element back where it was before `add`. `layout.freeRect` is the `fill` region, the space the world gets; `onChange` reports every re-layout. `layout.setForms(forms | null)` lays a scene's own tracks over the spec's, per form factor and field by field, for regions that follow the scene's content; the scene sets it on enter and on resizes and clears it on exit. `layout.dockCaption()` moves the caption card into `captionLane` (`caption.dock(host)`); undocked, the card sits in a frame corner and a game steers it with `caption.onPlace` and `caption.relayout()`. The layout owns `--tc-tap-min` (44 on touch forms), `--tc-text-min`, `--tc-region-pad`, `--tc-safe-*-px` and `--tc-modal-*`; buttons, toggles, sliders and panels honour them. `--tc-text-scale` and `scaleFontSizes` are in `ui/text-scale.ts`; `platform/device-mode.ts` (`data-phone`, `data-touch`) and `ui/rotate-card.ts` are interim API; the phone stylesheets stay in the game (`ui/phone-base.ts` and each scene's `*-phone-styles.ts`). *Planned:* ws/camera (D-044) feeds `freeRect` to `Camera.fitRect` and deletes `device`, `setFill` and the fill bands.

**Two overlays (history, ws/port-chrome).** Between ws/port-chrome and ws/one-overlay the engine ran two overlays: `ctx.ui`, the legacy 1920×1080 overlay shrunk by one CSS `scale()`, and `ctx.chrome` (`createCssChrome`), a CSS-px overlay with the layout on it, into which the legacy `panels` and `toasts` layers moved while a phone form factor was active (`cssForms`). It let a game port its scenes one form factor at a time. ws/one-overlay (D-044) deleted it: `createCssChrome`, `CssChrome`, `CssChromeOptions`, `PHONE_FORMS`, `EngineCtx.chrome`, `CreateGameOptions.overlay`, `createOverlay({ legacyScale })`, `overlay.setRect`/`onRect` and `caption.avoid()` are gone, and panels and toasts never move between roots. See CHANGELOG.md, "Removed (ws/one-overlay)".

**UI, Audio, Save, FX, Post.** The APIs are unchanged; the overlay's scaling model is the one change inside UI. *Today:* `ui/` (overlay stack, panels, widgets, toasts, captions, loupe, external-link widget, theme tokens), `audio/` (WebAudio buses, synth, recipes, mixer persistence), `save/` (versioned slots, migrations, quota- and blocked-storage-safe), `fx/` (GPU particles, flicker) and `post/` (bloom, god rays, fog, vignette, grade, quality tiers). Each module has a README with usage. `save` takes its storage from the host (`host.storage`).

**Analytics.** Typed, batched game events handed to a sink the game supplies; the engine makes no network call (VISION rule 4). *Today:* `createAnalytics<E>({ sink, session?, clock?, context?, onError?, maxBatch? })` in `analytics/` returns `emit(name, props)`, `flush()` and `attach(ctx)`. Each event carries `name`, `props`, a per-page-load `session`, a monotonic `seq` and `t`. `attach` emits `game_start` (form factor, host kind, DPR, viewport, embed, build), wraps `ctx.hooks.hide`, `show` and `deviceLost` (the game's hooks still run), emits `device_lost`, and on `hooks.hide(reason)` (hidden, pagehide, freeze) or device loss emits `session_end` with that reason and flushes; `show` re-arms it. It adds no lifecycle listeners of its own. A failing sink goes to `onError`; `emit` and `flush` never throw. *Planned:* a template-provided `sendBeacon` sink in the game template, and `level_start` / `level_complete` conventions.

**Scene and Ctx.** `Scene<Ctx, Frame>` and `SceneStack` are in `core/`. *Today:* `createGame(opts)` in `core/game.ts` (exported from the root entry `@thunderclap/engine`, not `./core`, because it is the top layer and pulls in every module) builds the engine's ctx and resolves to `EngineCtx`, or to `null` when WebGPU is missing (the unsupported screen is shown). It blocks browser zoom (double-tap, pinch, ctrl+wheel; option `blockBrowserZoom`, default on), boots the letterboxed surface, and builds the renderer, post stack, particles, host, save (`opts.save(host)`, opt-in), overlay, pad nav, device mode, audio (with `persistMixer` when `mixerKey` is set) and input (blocked under a modal). It wires resize (renderer, the overlay's frame via `ui.setFrame`, which re-lays the layout, phone scale, fill bands), the loop (input → pad nav → `hooks.update` → particles → scenes, in fixed steps of `sim.step`, default 1/60; `hooks.beforeRender` → scenes → `hooks.afterRender`), page lifecycle (hidden, pagehide, freeze: stop the loop, `hooks.hide(reason)` with `HideReason` `'hidden' | 'pagehide' | 'freeze'`, flush the save; shown: resume the loop, then `hooks.show(reason)`, unless the device was lost) and device loss (halt the loop for good, `hooks.deviceLost`, halt audio, flush, reload screen). Two parts are opt-in so a pure client of a server-authoritative game (VISION pillar 6) boots through the same call: **save**: without `opts.save`, `S` is `null`, `ctx.save` is `null` (typed `null`; such a ctx is not assignable to `EngineCtx<A>`, whose default `S` is `FlushableSave`, and `createGame` does not infer `S` from a return annotation), hide and device loss flush nothing, and nothing reads `host.storage` (leave `mixerKey` out too); **sim**: `opts.sim: false` runs the loop at render rate (`GameLoopOptions.fixed: false`), so input → pad nav → `hooks.frame(dt)` → particles → scenes' `update(dt)` run once per rendered frame with the real delta and `hooks.update` never runs. Callers that pass `save` and no `sim` get exactly the old behaviour. The harness's `game.html?mode=client` boots that way (e2e/client.spec.ts). `EngineCtx<Action, Save, Ctx>` (`Save extends FlushableSave | null`) holds `design`, `surface`, `gpu`, `renderer`, `post`, `particles`, `input`, `padNav`, `audio`, `ui` (the one overlay, with its layout as `ui.layout`; `CreateGameOptions.layout` is its `LayoutSpec`), `host`, `device`, `save`, `stack`, `loop`, `hooks`, `setFill(key)` and `onDeviceLost(fn)`. A game widens that same object with its nouns (`Object.assign(engine, {...})`), so scenes get one ctx; Last Rune's `GameCtx extends EngineCtx` in `games/last-rune/game/ctx.ts` (in the game repo, not here). *Planned:* `camera` and `gestures` join `EngineCtx` in Phase 3; the layout stays on `ui`. `device` and `setFill(key)` (with the fill bands) are interim phone concepts; ws/camera deletes them in favour of `layout.freeRect` and `Camera.fitRect` (D-044). The fixed pipeline (post, particles, audio, pad nav, loop order) opens up in ws/render-call.
