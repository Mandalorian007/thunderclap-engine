# ThunderClap engine: architecture and contracts

`@thunderclap/engine` is the WebGPU engine The Last Rune is built on. It knows nothing about any game. This file is the target the PM reviews promotions and public API changes against (D-041, [refactor plan](https://github.com/Mandalorian007/last-rune/blob/main/docs/engine/refactor-plan.md)). Decision numbers (D-0xx) and `docs/` paths in this repo refer to [The Last Rune](https://github.com/Mandalorian007/last-rune), where the engine was built. Each contract says what exists **today** (0.2.0-alpha.1 plus the unreleased work in CHANGELOG.md) and what is **planned**, with the workstream that delivers it.

## Package shape

```
thunderclap-engine/
  package.json        # @thunderclap/engine; the "exports" map is the public API
  pnpm-workspace.yaml # packages: ['packages/*']; the engine stays the root package
  packages/
    host-electron/    # @thunderclap/host-electron: the Electron shell (main, preload) and
                      # createElectronHost(); depends on the engine via "workspace:*" (links the root)
  src/
    index.ts          # the "." entry: createGame and its types
    analytics/  anim/  assets/  audio/  core/  fx/  geom/  host/  i18n/  input/  nav/  platform/  post/  render/  save/  ui/
  harness/            # noun-free e2e pages: index.html boots the platform layer (window.__harness);
                      # game.html boots through createGame (window.__harnessGame); rays.html, mesh.html,
                      # views.html, stream.html, weather.html, look.html, anchors.html, gltf.html and
                      # xr.html use cameras; ui.html, layout.html and gestures.html are DOM only
  e2e/                # engine e2e specs, fixtures, ports, itch-style iframe wrapper
  templates/          # copyable games (puzzle, first-person); `pnpm create-game <dir> --template <name>`
                      # (scripts/create-game.mjs) copies one out as a standalone project on the engine
  playwright.config.ts  # the viewport/device/wrapper matrix every engine spec runs on
  ARCHITECTURE.md     # this file
  CHANGELOG.md
```

**Test ownership (D-041 addendum 2).** The engine verifies platform capability once, for every game: unit tests (`src/**/*.test.ts`, Vitest) and e2e specs (`e2e/`, Playwright) run against the `harness/` page. Every spec runs on the whole matrix in `playwright.config.ts`: desktop 1280×720 and 1920×1080, iPad 1180×820, four phones (667×320, 844×340, 932×380, 915×360, touch at DPR 2), and the harness inside an itch-style cross-origin iframe. Two upright rows, `phone-port` 390×844 and `tablet-port` 820×1180, run the layout spec only. A new platform capability (host, gestures, layout, lifecycle) adds a probe to the harness and a spec here, not in a game. Games test product only. `pnpm bench` runs the scene ladder in `harness/bench.html` and rewrites `docs/BENCH.md` (ws/bench).

Games import only the exports map: `@thunderclap/engine` (the `"."` entry: `createGame` and its types) and `@thunderclap/engine/<module>` for `analytics`, `anim`, `assets`, `audio`, `core`, `fx`, `geom`, `host`, `i18n`, `input`, `nav`, `platform`, `post`, `render`, `save`, `tween` and `ui`, plus `@thunderclap/engine/testing` (the recording fake `GPUDevice`, for unit tests only). Each subpath is that module's `index.ts`; anything not re-exported there is internal. `pnpm check:boundaries` (`scripts/check-boundaries.mjs`, part of `pnpm check`) fails if anything under `src/` imports from outside `src/` or through the package name, or if `harness/`, `e2e/`, `examples/` or `templates/` imports a subpath outside the map or reaches into `src/` by a relative path. Inside the package, modules import each other by relative path. A game, in its own repo, is held to the same map by its own checks.

**Workspace.** The engine is the root package, so a dependency on this repo by URL still resolves to it. `packages/host-electron` is a workspace package that depends on the engine with `"workspace:*"`, which pnpm links to the root. It is self-contained: the root `tsconfig.json` does not include `packages/`, and `pnpm check` runs `check:host-electron` (typecheck, lint, unit tests) after the engine's own checks. Desktop builds go to `dist/desktop/` at the repo root (gitignored). The engine never imports the package.

The package ships TypeScript source; the game's Vite build compiles it. There is no separate engine build until Phase 5 (extraction and publishing). A game starts in its own repo with `pnpm create-game <dir> --template <name>` (ws/scaffold): the template is copied out of `templates/`, its `package.json` renamed and pointed at the engine by version (or `--engine <spec>` for a `link:`, `file:` or `github:` spec), and its `CLAUDE.md` kept; `pnpm check` scaffolds and typechecks one (`check:create-game`).

## Ground rules

1. **Promotion rule.** Code enters the engine only if Last Rune uses it, the next game plausibly would, and its API has zero game nouns.
2. **Dependency direction.** `games/*` imports `@thunderclap/engine`; the engine never imports a game. A game's `rules/` imports nothing from the engine or the DOM.
3. **No runtime dependencies** without a DECISIONS entry (D-008). WebGPU is the only renderer.
4. **Seams, not features.** 3D and XR arrive capability by capability with the game that needs them (VISION rule 6). The engine grew the seams first (`Surface`, `Camera`, the frame loop, `Host`, `PointerSource`) and then XR through them (ws/xr, E-013): XR is *Today* behind `createGame({ xr })` (`XrSurface`, `createXrHost`, `XrPointerSource`, `ctx.xr.enter()/exit()`), with no redesign of the 2D path, which stays pixel-identical. The post stack runs per eye through `renderer.resolve` (ws/xr-post). Nothing XR-specific waits for Gate 5; what comes after Gate 5 is whatever the next game names.

## Contracts

**Surface.** Owns the canvas, the swapchain, DPR, the backbuffer size and the letterbox fit. It exposes `rect` (CSS px), `backbuffer` (device px), `clientToLogical` and `onResize`. *Today:* `Surface` / `mountSurface` in `platform/surface.ts` exposes `rect`, `fitRect`, `backbuffer` (device px), `clientToLogical`, `logicalToClient`, `containsLogical`, `onResize` and `setFrame(rect | null)` (letterbox inside a part of the container, CSS px, e.g. the layout's `freeRect`), over the pure letterbox math in `platform/letterbox.ts` (`computeLetterbox`, `computeBackbuffer`, `clientToLogical`, `logicalToClient`); `initGpu` configures the swapchain. The fill-width fit (`setFill`, `computeFillWidth`, `FillWidthOptions`) is gone (ws/plumbing, E-010): a 2D game frames `ui.layout.freeRect` with `Camera.fitFreeRect(worldRect, freeRect, surface)` (D-044). The renderer draws into a `SceneTarget` through `renderer.render(frame, camera, target)` (ws/render-call). `XrSurface` in `platform/xr-surface.ts` (ws/xr) is the per-eye counterpart, a separate class rather than a `Surface` (no `rect`, `backbuffer` or `onResize`; the headset owns those): an `XRGPUBinding` projection layer in `SCENE_FORMAT` + `depth24plus`, and per frame `views(frame): XrEyeView[]`, each with a depth-on `Camera` (`viewIndex` 0/1, the view's projection and inverse pose, `screen` the viewport fraction) and a `SceneTarget.external(...)` over the layer's `getViewSubImage` colour and depth textures (one shared target when the eyes are side by side on one texture, so the first eye clears and the second loads). With `scene: true` (ws/xr-post, what `createGame` passes) the surface also keeps `scene`, one eye-sized HDR `SceneTarget` (allocated on the first posed frame, resized on eye-size change), the eye cameras cover it whole, the layer is made in the post stack's output format (`renderer.format`) without depth, and each eye is rendered into `scene` and resolved into its `viewport` of the layer.

**Camera.** A view-projection matrix plus `worldToScreen` and `screenToWorld` (the inverse projection; touch aiming uses it). Presets: `ortho2d(designW, designH)`, where 1 unit = 1 design px, and `fitRect(rect, viewport)`, which fits a world rect into a viewport. Depth test and depth write are camera-preset flags; the 2D preset leaves both off. *Today:* `Camera` in `render/camera.ts` (ws/camera) holds `view`, `projection` and `viewProjection` (column-major `Float32Array(16)` from `mat4` in `core/math.ts`, `@thunderclap/engine/core`; cached, recomputed on read after a change), `position`, `depthTest`, `depthWrite`, a `layers` membership mask (u32, default all bits; the draw sort `order` belongs to ws/transforms) and `screen`, the rect clip space spans in the units `worldToScreen` returns and `screenToWorld` takes. `Camera.ortho2d(w, h)` is origin top-left, y down, and looks down +z (right-handed with y down: larger z is farther), spanning world z in ±`ORTHO2D_HALF_DEPTH` (1024; z = 0 sits at clip depth 0.5), with `screen` = the design space; its 2D controls `x`, `y`, `zoom` and `rotation` are the earlier 2D camera's, and its `viewProjection` uses the same arithmetic, so the 2D path is pixel-identical. `fitRect(rect, viewport = screen)` sets those controls (rotation 0) so a world rect is contained and centred in a viewport given in screen units. `Camera.perspective(fovY, aspect, near, far)` is right-handed, looks down -z, turns depth on and is placed with `lookAt` or `setView`; `screenToWorld(sx, sy, 0)` and `(…, 1)` give a pick ray. `setPerspective(fovY, aspect, near, far)` on any camera sets the same depth and cull flags (`setProjection` stays raw), and the per-frame helpers `viewZ`, `invViewProj`, `projectMany` and `frustumCorners` (ws/camera-ergo) project many points or read the frustum without allocating. `renderer.camera` is `Camera.ortho2d(logicalWidth, logicalHeight)` by default and can be reassigned. Each frame the renderer writes the camera block (`EngineCamera` at `@group(0) @binding(1)`: `view`, `proj`, `view_proj`, `camera_pos`, `viewport` in scene target px, `view_index` = `camera.viewIndex`, default 0) beside the globals (`@binding(0)`: `logicalSize`, `targetSize`, `time`, `dt`) in one upload, and `engine_vertex` projects with `camera.view_proj`. The renderer reads `layers` (draws with `layers & camera.layers === 0` are skipped), `depthTest` (off: no depth attachment, draws sorted by `order` then submission), `depthWrite` (both flags off for `ortho2d`, on for `perspective`) and `viewProjection` (clip-space depth is the depth sort key, so the sort agrees with the depth buffer for every projection) from the camera passed to `render(frame, camera, target)` (ws/render-call); the clip line is `camera.view_proj * vec4(world.xyz, 1)`, so the instance's world z reaches the depth buffer. `fitFreeRect(rect, freeRect, surface)` takes the layout's `freeRect` in CSS px, maps it onto `screen` through `surface.rect` and fits the world rect into it, allocating nothing (ws/plumbing). Per-eye cameras (ws/xr): `setViewMatrix(m)` (an alias of `setView` for an `XRView`'s `transform.inverse.matrix`) and `setProjection` take the headset's matrices; `XrSurface` keeps one `Camera` per eye with `viewIndex` = eye and `depthTest` on.

**Transforms, layers and instances.** Every draw is one 28-float instance whose placement is a 3×4 world matrix, so 2D sprites, meshes and later voxels share one vertex path. *Today:* `render/transform.ts` exports `Transform` (position xyz, rotation about Z for 2D as `rotation` in radians, or any 3D rotation as a unit quaternion via `setQuaternion` / `setAxisAngle`; scale xyz; optional `parent`) with a cached 3×4 row-major `world` matrix that recomputes only when it or an ancestor changes. `frame.sprite(mat, DrawParams)` still works and writes the matrix directly (`writeMatrix2d`, exact at rotation 0, no allocation); `frame.sprite(mat, transform, params?)` and `frame.mesh(mesh, mat, transform, params?)` take a `Transform`. Every draw carries `layers` (u32, default 1) and `order` (sort key, default 0). Without depth, draws sort by `order` then submission index, so the default reproduces submission order and batching exactly. With `camera.depthTest`, keys are `order`, then opaque before blended, then clip-space depth from the render camera (opaque front-to-back, blended back-to-front), then submission index; the depth24plus attachment is allocated only then. Meshes carry a `VertexLayout`: `VERTEX_LAYOUT_2D` (8 floats, unchanged; `quadGeometry()` unchanged) or `VERTEX_LAYOUT_3D` (xyz, normal xyz, uv, rgba = 12 floats). Materials build pipelines lazily per (vertex layout, depth mode) from a per-layout prelude (`materialPrelude(layout)`), so a game's `fs_main` is unchanged. A `Mesh` has a `capacity` (vertices, indices; `createMesh` takes initial data, a capacity or both) and `update({ vertices?, indices?, vertexCount?, indexCount? })`, which writes each view in place from its own `ArrayBuffer` (a buffer transferred from a Worker is uploaded without a main-thread copy), reuses the GPU buffers while the counts fit, grows them 1.5× only when they do not (`growths` counts it) and lets `indexCount` shrink the draw without reallocating, and also takes a Worker's reply as-is (`MeshReply { buffer, vertexCount, indexCount?, indexOffset?, bounds? }`, ws/ergo-3d); `harness/stream.html` streams chunk meshes from a Worker this way. An indexed mesh with `indexCount` 0 draws nothing. `VERTEX_LAYOUT_SKINNED` (ws/skinning: the 3D layout plus `uint8x4` joints and `unorm8x4` weights, 56 bytes) skins on the GPU: the material binds a `SkinPalette` (a storage buffer of 3×4 joint matrices, 12 floats each, `instances × joints`, the layout `anim`'s `skinMatrices` writes; `BindingDesc.buffers` at `@group(1) @binding(16)`), the draw names its slot in `params.w`, and `materialPrelude` emits `WGSL_SKIN` (`engine_skin`) only for that layout so `engine_vertex`, the shadow pass's `vs_main` and the 2D/3D preludes are unchanged; the shadow pass binds the material group as group 1 for a skinned caster, so its shadow follows the pose. Drawables declare depth themselves: `ParticleSystem.draw(pass, frame)` picks a pipeline with `depthStencil { format: frame.depthFormat, depthWriteEnabled: false, depthCompare: 'less-equal' }` (one per format, built lazily) when the frame has depth. Each mesh draw also carries `mesh.bounds` (a bounding sphere: given with the geometry or computed from the positions) through its instance matrix into a world sphere (ws/cull). Instance `flags` (float 25, `VSOut.flags`) carry `receiveShadow: false` in bit 0 (ws/shadows); the other bits are reserved.

**Animation.** Clips are data, sampling is arithmetic, and the renderer sees only matrices: a mixer blends keyframe clips into a pose, the pose resolves into node world matrices for anything that follows a bone (cosmetics on sockets, a weapon in a hand) and into joint matrices for skinning (E-015). *Today (ws/anim):* `@thunderclap/engine/anim` (`anim/`) is pure TypeScript with no GPU and no `render/` import. `AnimationClip { name; duration; channels; events? }` and `AnimationChannel { node; path: 'translation' | 'rotation' | 'scale' | 'weights'; interpolation: 'STEP' | 'LINEAR' | 'CUBICSPLINE'; times; values }` carry glTF sampler semantics one to one (cubic-spline in/out tangents, hold outside the key range), so the glTF importer fills them without conversion. `sampleClip(clip, t, pose, weight, blend, cursor?)` writes into a `Pose` (10 floats per node: `t3 q4 s3`, `POSE_NODE_FLOATS`) by override (lerp/slerp) or additive (deltas) blending, with a per-channel keyframe cursor so forward playback is O(1) amortised. `Skeleton { parents; rest; inverseBind?; joints? }` is parent-before-child; `poseToWorld(skeleton, pose, out)` writes 3×4 row-major world matrices in the `render/transform.ts` convention (12 floats per node, `WORLD_NODE_FLOATS`), and `skinMatrices(skeleton, world, out)` writes `world[joint] · inverseBind` in the same 12-float-per-joint layout `render/skin.ts` uploads (glTF 16-float column-major inverse bind matrices are converted on the fly; `inverseBindFromRest` builds them for procedural rigs). `AnimationMixer(skeleton)` holds a fixed pool of `AnimationAction`s: `play(clip, { layer, weight, loop, speed, fadeIn, blend, startTime })`, `crossFade(from, to, seconds)` (effective weights sum to 1 throughout), `stop(action, fade?)`, `update(dt)` → `mixer.pose` (per layer ascending: override actions averaged by weight and lerped on by `min(1, Σ)`, then additive actions), and `onEvent(cb)` for `clip.events` crossings, once each, across loop wraps. Quaternion helpers (`quatSlerp`, `quatNlerp`, `quatMultiply`, `quatFromEuler`, …) work in place on flat arrays. Sockets (ws/sockets) attach cosmetics to joints: `createSocket(skeleton, joint | name, { position, rotation, scale })` (names through `Skeleton.names`) gives a `Socket { joint; offset }`, `socketWorld(socket, world, instanceWorld, out)` writes `instance · world[joint] · offset`, and `attachTransform(...)` puts it into a `Transform` (`Transform.setMatrix`) so the attached mesh draws through `frame.mesh` unchanged. `createAnimGraph(mixer, desc)` (ws/anim-graph) puts a state graph over the mixer: states hold a clip or a 1D blend space whose two nearest points share the weight with one synced phase across their clips, transitions carry a condition over a shared parameter object, a fade and an optional exit time, and every state's weight lerps toward the target so the weights sum to 1 throughout. Nothing allocates per frame after setup. IK and root motion (ws/ik) are pose arithmetic between sampling and the final `poseToWorld`: `twoBoneIk` (analytic, pole vector, weight) and `lookAt` (forward axis, up hint, angle clamp) read the sampled pose's world matrices and write local rotations, and `extractRootMotion` splits a clip into an in-place clip and a `motion` clip whose `applyRootMotionDelta` gives the game a heading-frame position delta and a yaw delta, loop wrap included. *Today (ws/retarget):* `createRetargetMap(source, target, { pairs?, match?, rootNode?, scaleTranslation? })` pairs the joints of two skeletons (explicit pairs, exact names, then a lowercase separator-stripped compare of `Skeleton.names`; leftovers in `map.unmatched`) and precomputes per target joint the two rest-frame quaternions `pre`/`post` with `Rt = pre · Rs · post`, the source joint's rest-relative delta in its parent frame carried into the target parent's frame; `retargetPose(map, sourcePose, targetPose)` applies them with no allocation (translations stay at the target rest except the root's, scaled by the hip-height ratio), and `retargetClip(map, clip, { sampleRate?, name? })` bakes a clip to the target once. Morph targets (ws/morph) blend on the CPU: `createMorphBlender(base, targets, layout)` → `MorphBlender` writes `base + Σ weight × delta` into the position and normal lanes of an interleaved vertex buffer (normals renormalised) and reports whether anything changed since its last apply, so a mesh uploads through `Mesh.update` only on a change; `sampleWeights(clip, node, t, out)` samples a `'weights'` channel with `sampleClip`'s rules. *Planned:* full-body IK when a game names them.

**Tweens.** Every game moves numbers over time: a menu slides in, a camera eases to a target, a hit flash fades. The engine owns the arithmetic and the bookkeeping, not the clock. *Today (ws/tween):* `@thunderclap/engine/tween` (`tween/`) is pure TypeScript with no GPU and no import outside itself. `createTweens()` returns a `Tweens` manager a game ticks with `update(dt)` from its frame or update hook; it holds root tweens in one array, compacts it in place, and allocates nothing after setup. `to(target, props, seconds, opts)` animates number fields by dotted path (`'x'`, `'position.0'` into a `Float32Array`, `'style.opacity'`), resolving the paths to holders and keys when the tween is created and reading start values when it starts, after its delay; `value(from, to, seconds, onUpdate)` reports one number; `delay(seconds)` is a gap or a timer; `sequence(...)` and `parallel(...)` are tweens of tweens that carry a child's leftover `dt` into the next child, so a long frame drifts nothing. `TweenOptions` carry `ease`, `delay`, `loops` (`-1` forever), `yoyo` (groups play their children backwards), `onStart`/`onUpdate`/`onComplete` and `timeScale`; the `Tween` handle has `progress`, `elapsed`, `duration`, `pause`/`resume`, `kill`, `restart`, `then(fn)` and `promise()`. A tween killed or created from a callback inside `update` is safe. The easing table `ease` holds the Penner set (`quad`…`bounce`, `In`/`Out`/`InOut`), `linear`, `smoothstep`, `steps(n)`, `cubicBezier(x1, y1, x2, y2)` and `spring(stiffness, damping)`: a `SpringEase` is a description, not a function of `t`, and a tween given one has no duration, integrates the spring in bounded substeps and completes when it settles. `post/blend.ts` imports `Ease` and the four functions it used to define from here (`easeLinear`, `easeIn`, `easeOut`, `easeInOut` stay as aliases), so there is one easing table. *Planned:* nothing on spec; colour-space interpolation when a game asks for it.

**Navigation.** Finding a way is arithmetic over the game's own map, and the renderer never hears of it: a grid of walkable cells with costs, a search that fills a path the game follows, a flow field that one build serves a crowd with, and steering that keeps agents apart. Navigation is 2D over world `x` and `z`; height is the game's business (sample the terrain when placing the agent). *Today (ws/nav):* `@thunderclap/engine/nav` (`nav/`) is pure CPU with no import from any other engine module and no allocation per query after warm-up. `createNavGrid({ width, height, cellSize, origin?, walkable?, cost? })` gives a `NavGrid` (`costs: Float32Array`, 0 = unwalkable; `setWalkable` / `setCost` bump `version` on every real change; `toCell` / `toWorld`). `findPath(grid, from, to, out: NavPath, opts?)` is A* with a binary heap over per-grid scratch arrays (a `WeakMap`), octile heuristic, step cost `(1 | √2) × cost(dest)`, no corner cutting (a diagonal needs both orthogonal neighbours walkable), and `maxExpand`; it writes world-XZ cell centres into a `NavPath { points: Float32Array; length; cursor; version }` stamped with `grid.version`, so a changed wall marks the path stale. `smoothPath` string-pulls it in place over `hasLineOfWalkable` (an integer supercover line). `followPath(path, position, speed, arriveRadius, outVelocity)` returns `'moving' | 'arrived'`. `createFlowField(grid).build(goals)` is Dijkstra from the goals into `distances` and unit `directions` per cell (`directionAt(worldX, worldZ, out)`). `steer.separate`, `steer.arrive` and `steer.avoidDisc` write velocities. `harness/nav.html` (no WebGPU) and `e2e/nav.spec.ts` prove a path around a wall, rerouting on a toggled wall and 32 agents arriving within a bound of fixed-step sim time on every matrix row. *Today (ws/nav-2):* for non-grid worlds, `bakeNavMesh` voxelises world triangles Recast-style into a `NavMesh` of convex polygons with 3D heights, `findMeshPath` is polygon A* with funnel string pulling into a `NavPath3` that names the off-mesh links (`addOffMeshLink`) it takes, `createCrowd` is ORCA local avoidance and `exportNavMesh` / `importNavMesh` let a game bake at build time and ship bytes (`harness/navmesh.html`, `e2e/navmesh.spec.ts`). *Planned:* voxel-column grids when a game names them.

**Renderer.** The renderer records draws into a `Frame` and draws them for one camera into one target; it owns no camera and no frame of its own beyond conveniences. *Today:* `renderer.beginFrame(time, dt)` returns the reusable `Frame`; `renderer.render(frame, camera, target = renderer.target)` encodes one scene pass of the recorded draws for that camera into a `SceneTarget` (colour + emissive, `SCENE_FORMAT`, plus a `depth24plus` attachment made on first use by a depth camera); `renderer.endFrame()` runs post (or present) from `renderer.target` and submits, and calls `render(frame, renderer.camera)` itself when nothing rendered in between, so `createGame`'s single-camera path is unchanged. Several `render` calls per frame (split screen through `camera.screen`, which sets the viewport and scissor as a fraction of the target when it lies inside the unit square, else in logical px; UI over world through layers; an offscreen view through `renderer.createSceneTarget(desc)`) share one instance buffer at increasing offsets and one 2032-byte uniform buffer (globals, camera, lights) plus bind group per view (`engine-globals`, `engine-globals-1`, …; pooled, so steady state allocates nothing); the first view into a target clears it (colour from `frame.clearColor`, depth to 1), later views load. A view that sees a `Drawable` with `readsDepth` splits its scene pass at the opaque/blended boundary, copies the depth attachment into `SceneTarget.depthCopy` and calls the drawable's `afterOpaque(encoder, view)` before the blended pass, so depth-reading drawables (water, soft particles, decals) see this frame's opaque depth; frames without one encode exactly the passes they did before (ws/render-hooks). `renderer.stats` is reset in `beginFrame` and summed over the views. Each view's `view_index` is its camera's `viewIndex` (default 0), so a stereo pair is two `render` calls with `screen` the two halves and `viewIndex` 0 and 1 (ws/two-views; `harness/views.html` and `e2e/views.spec.ts` prove it on the matrix, with depth cleared once per target and each half's draws scissored to it). `Renderer.render` outside `beginFrame`/`endFrame` throws. Materials bind texture arrays: `TextureDesc.layers` makes a `'2d-array'` view, `loadTextureArray(device, sources, { mips })` uploads one image or pixel source per layer and builds the mip chain on the GPU (`generateMipmaps`, a cached blit pipeline per format, also for 2D textures made with `mips: true`), `viewDimension: '2d-array'` on a `MaterialDesc` or `FullscreenPassDesc` declares the slot as `texture_2d_array<f32>`, the `'linear-mip-repeat'` and `'nearest-mip-clamp'` samplers blend mips, and a 3D mesh carries a face's layer in its vertex colour's alpha (`harness/stream.html`; ws/texture-array). `loadTexture` builds a mipmapped 2D texture in one call and `defaultTextures(device)` supplies white/black/flat-normal/metal-rough/checker; every unset material slot binds white (ws/texture-registry). With `camera.cull` (the perspective default) a render call drops, before sorting, every mesh draw whose world sphere is outside one of the camera's six cached `frustum` planes and counts it in `renderer.stats.culled`; sprites, drawables and meshes without bounds are never culled, and the 2D path (`cull` off) is untouched (ws/cull). `endFrame({ present: false })` (ws/xr) skips the post or present step into the swapchain and only submits: an XR frame's eyes went to the session's layer and nothing goes to the canvas. `renderer.resolve(target, out, viewport?)` (ws/xr-post) is that post or present step for any target and any output view, inside the frame after a `render`: it runs `renderer.post` (or the built-in present) from `target` into `out`, confined to `viewport` (texture px, loading the rest) when given, and consumes the target so its next `render` this frame clears again. The XR step is `render(frame, eye.camera, surface.scene)` then `resolve(surface.scene, eye.target.color.view, eye.viewport)` per eye on the one encoder, so both eyes share one HDR target and the post stack's intermediates. `PostProcessor.encode(encoder, inputs, output, viewport?)` carries the viewport and a processor sizes itself to its inputs (`PostStack` resizes once when they change). `PostInputs.depth` and `PostInputs.projection` (`PostProjection { near, far, proj }`, ws/post-depth) hand the post processor the target's depth attachment and the projection of the camera that drew it, `null` on frames that rendered no depth, so depth passes can skip without touching the 2D path. Many instances of one mesh and material go through `frame.meshes(mesh, material, batch)` (typed arrays copied straight into the frame's upload, one sort key, culled per instance or as one sphere) or a retained `InstanceList` (`renderer.createInstanceList`, `frame.list`: its own vertex buffer, dirty-range uploads, swap-remove), so 50k cubes cost a few ms of CPU instead of one `frame.mesh` each (ws/batch-submit; `docs/BENCH.md`).

**Lighting.** The engine supplies light uniforms; the style (Lambert, toon, rim, none) is the game's WGSL, so a candle-lit dungeon and a sunlit overworld are two fragment shaders over one block. *Today (ws/lights):* `Lights` in `render/lights.ts` (ambient rgb, `sun { dir, color }`, `points: PointLight[]` of `position`, `color`, `radius`; `MAX_POINT_LIGHTS` = 16) is carried by the frame as `frame.lights`, which the game sets or mutates and which defaults to the unlit block (ambient 1, no sun, no points). The renderer writes it as `EngineLights` at `@group(0) @binding(2)` (snake_case: `ambient`, `point_count`, `sun_dir` normalised and pointing the way the light travels, `sun_color`, `points[16]` of `position`, `radius`, `color`, then `sun_view_proj`, `shadow_params` (bias, texel size, enabled), `fog` (rgb, density), `fog_range` (near, far), then `spot_count`, `sun_layers`, `point_layers[4]` (vec4u) and `spots[8]`; `LIGHTS_BLOCK_FLOATS` = 316) at byte offset 768 of each view's uniform buffer, in the same upload as the globals and the camera block (one buffer per view, 2032 bytes), and `renderer.globalsLayout` has the binding for every material and drawable, plus the sun's shadow map (`texture_depth_2d`, binding 3) and a comparison sampler (binding 4). `materialPrelude` declares the block plus `engine_point_lights(normal, world_pos)` (Lambert × `(1 - d/radius)²`), `engine_shadow(world_pos)` (3×3 PCF against the map; 1 when none), `engine_fog(color, world_pos)` (linear or exponential by distance from the eye; identity at density 0) and `engine_lambert(normal, world_pos)` (ambient + sun Lambert × shadow + points), which a material may call or ignore; with the default block `engine_lambert` is `vec3f(1)`, so `fs_main` contracts are unchanged and the 2D path is pixel-identical. *Shadows (ws/shadows):* `Lights.sun.shadow: SunShadow` (`extent`, `size` 1024/2048/4096, `near`, `far`, `bias`) makes the renderer encode one depth-only pass per `render` before the scene pass, through `render/shadow.ts` (`ShadowMap`: a `depth32float` map, an orthographic `Camera` centred on the view camera's position and pointed along the sun, a pipeline per vertex layout reusing the prelude's `vs_main`), over the view's opaque draws with `castShadow` (default: 3D layouts yes, `VERTEX_LAYOUT_2D` no, so 2D frames never run it); the shadow list is culled against the sun box, not the view frustum (`stats.shadowDraws`); a 1×1 depth placeholder is bound until the first shadow pass (after it the last map stays bound and `shadow_params.z` = 0 makes `engine_shadow` return 1), so one layout serves both. `receiveShadow: false` is instance flag bit 0 (`VSOut.flags`) for materials to read. `Lights.fog: Fog` (`color`, `density`, `near`, `far`) feeds `engine_fog`. `Lights.writeBlock(f32, u32, offset, shadow?)` allocates nothing; `harness/mesh.ts` lights its scene with a shadowing sun, fog and a circling point light. *Spots and masks (ws/spot-lights):* `Lights.spots: SpotLight[]` (`position`, `direction`, `color`, `radius`, `innerAngle`, `outerAngle`; `MAX_SPOT_LIGHTS` = 8) and an optional `layers` mask on every light are appended to the block after fog, the instance's low 23 layer bits ride in the flags float above the shadow bit (`packInstanceFlags`), and the prelude gains `engine_light_accum(world_pos, normal, layer_mask)` (sun × shadow + points + spot cones of the lights whose mask shares a bit), `engine_lambert_layers` and `engine_instance_layers(flags)`, with `engine_lambert` unchanged in signature and spanning every layer; `harness/lights.html` sweeps a spot beside a masked point light. **Materials.** `createStandardMaterial` (`render/standard.ts`, ws/pbr) is the one material a game needs before writing WGSL: glTF metallic-roughness PBR over the same lights block, with `WGSL_PBR` exposing its BRDF and derivative-based normal mapping to custom shaders; since ws/pbr-lights the Lambert helpers and the PBR material run one generated light loop (`wgslLightLoop(name, brdf)`: sun × shadow, points, spot cones and layer masks, with the BRDF expression inlined because WGSL has no function pointers), so every light the prelude sees, every material sees. *Planned:* cascades when a game needs them.

**Frame loop.** `GameLoop` runs a fixed 60 Hz update and a variable render; the camera and the target are inputs to the render path (`Scene.render(frame, camera, alpha)`, `renderer.render(frame, camera, target)`), not state read from the renderer. The host decides who schedules frames (rAF, Electron, `XRSession.requestAnimationFrame` through `createXrHost`); `GameLoop.setFrames(src)` swaps the source while running (ws/xr). *Today:* `GameLoop` and `FixedStepper` in `core/loop.ts` (fixed step, `maxFps` cap, pause) call `render(alpha, time)` from the frames of a `FrameSource` (`GameLoopOptions.frames`: `createGame` passes its `Host`; the default is `defaultHost()`, read on the first `start()`; tests pass a stub they step by hand). The loop never calls `requestAnimationFrame` itself. The game's render callback records a `Frame` and calls `renderer.render(frame, camera, target?)` per camera (or lets `endFrame` render `renderer.camera`). With `GameLoopOptions.fixed: false` (what `createGame({ sim: false })` uses) there is no accumulator: `update(dt, time)` runs once per rendered frame with the real clamped delta, `render` gets `alpha` 1, and pause still skips update. `Scene<Ctx, Frame, Cam = Camera>` and `SceneStack` in `core/scene.ts`: `Scene.render(frame, camera, alpha)` takes the camera from the game (`SceneStack.render(frame, camera, alpha)` forwards it), so no scene reads `renderer.camera`; `createGame` passes `ctx.camera` and then calls `renderer.render(frame, ctx.camera)` itself (ws/plumbing, E-010).

**Host.** `interface Host extends FrameSource { kind; requestFrame; cancelFrame; openExternal; copyText; clipboardWriteAllowed; fullscreen; storage; window?; embed }`. Implementations: `web` (detects iframe vs top and wraps today's D-036 link service) and `electron` (preload bridge). The engine never calls `window.open`, `navigator.clipboard` or `localStorage` directly. *Today:* `host/` (`@thunderclap/engine/host`) has the `Host` type, `createWebHost({ win? })` and `defaultHost()` / `setDefaultHost()`. `clipboardWriteAllowed()` says whether `copyText` can write without a prompt; `fullscreen` is `{ available, active, toggle, watch }` and `storage` is `{ kind, open(): StorageLike | null }`. `save` (`createSaveStore`, `listSlots`), `persistMixer` and the `externalLink` widget take `host` and default to `defaultHost()`. `window.open`, `navigator.clipboard`, `execCommand` and `localStorage` appear only in `host/web.ts` and `host/web-links.ts`; the fullscreen DOM calls stay in `platform/device.ts`, which the web host wraps. The Electron host lives in this repo as `packages/host-electron` and provides `createElectronHost()` (`@thunderclap/host-electron`): the same interface over the preload bridge `window.thunderclap`, `kind: 'electron'`, storage the renderer's `localStorage` (served from the fixed origin `app://bundle`), and `window` with `close`, `minimize`, `toggleMaximize` and `setTitle`. A game installs it with `setDefaultHost` or passes it to its ctx; the engine never imports it. Frames come from the host (ws/render-call, D-044): `FrameSource { requestFrame(cb: (timeMs) => void): number; cancelFrame(handle) }`, wrapped over the window's `requestAnimationFrame` on web and Electron; `GameLoop` schedules through it, so an XR session is a `Host` implementation (`XRSession.requestAnimationFrame`), not a redesign: `createXrHost(session, base)` (ws/xr) returns an `XrHost` (`kind: 'xr'`) whose frames come from the session, which exposes the current `XRFrame` on `frame` during a callback, and which delegates everything else to the page host; `createGame({ xr })` moves the loop onto it with `loop.setFrames` on `ctx.xr.enter()` and back on exit or the session's `end` event. Three optional facets serve a phone shell and the browser alike (ws/host-mobile): `lifecycle` (`state(): 'active' | 'background'`, `watch`; `createGame` stops frames and flushes the save on `background`, restarts on `active` and calls `hooks.lifecycle`), `haptics` (`available`, `impact`, `notification`, `vibrate`; `navigator.vibrate` on the web) and `safeArea` (`insets()` in CSS px, `watch`; `createGame` pads `ui.layout` through `followSafeArea`), and `packages/host-capacitor` (`@thunderclap/host-capacitor`, `kind: 'capacitor'`) fills the interface from Capacitor's plugins handed in at construction (browser, clipboard, screen orientation, a Preferences-backed `storage`, `appStateChange` lifecycle, native haptics, an Android `back` watcher), never importing them.

**Input.** The action map for keyboard, mouse, touch, pen and gamepad, with `blocked()`, `lastDevice`, queued taps, iframe-safe `preventDefault`, injectable pads and public feed methods for tests; `ui/padnav.ts` drives modal panels from the pad and `ui/menu-nav.ts` (`menuNav`) drives non-modal menus. `Gestures` (`input/gestures.ts`) recognises tap, double tap, long-press (450 ms), pan, drag (with its origin) and pinch (scale) from pointer events, with thresholds in CSS px (pan 10) and positions in game space through the same `PointerTransform`; while two or more pointers are down, pan and drag report nothing (a second pointer cancels them and starts the pinch, ws/plumbing). It reports per tick like `Input`: one discrete gesture per kind per tick (extras queue), continuous ones every tick from `start` to `end` or `cancel`; travel is cumulative from the down point and the pan threshold is checked before the long-press timer on every move, so a slow drag under a long frame pans and never long-presses (ws/gesture-longpress), and `gestures.onGesture(listener)` observes each recognition synchronously, for tests and logging rather than game logic. `input.setGestures(g)` (or the `gestures` constructor option) links it: the gestures share `blocked()` and the transform, attach with `Input.attach`, advance in `Input.update()`, and can be bound as actions (`{ gesture: 'tap' | 'doubleTap' | 'longPress' | 'pan' | 'drag' | 'pinch' }`), so a game can map tap to `select` and long-press to `info` without reading gestures; `createGame` builds the `Gestures` (`CreateGameOptions.input.magnify` is its `magnify`) and exposes them as `ctx.gestures`. While blocked nothing is reported and a running pan, drag or pinch gets one `cancel`. The `magnify` option (`input/magnify.ts`, ws/port-altar) is loupe and snap for small touch targets: while one touch pointer is down each tick reports `gestures.aim`, the finger raised by `lift` (56 CSS px) while it drags, snapped by the game's `snap(x, y)` (usually `snapToGrid`, the nearest accepted cell within half a pitch), and while `pitch()` is below `below` (44 CSS px) a `Loupe` beside the finger magnifies the aim point `zoom` (2.5) times with the target ringed. The aim the finger lifted at is reported once more (`ended`) on the drag's `end` tick, so a dragged thing lands where it was aimed. Mouse and pen never aim. The loupe and its leader line (dense-board-4) are `position: fixed` elements in client px outside the overlay's layers, so overlay units never apply to them. *Today (ws/input-rays):* every pointer is a ray. `createPointerRouter({ camera, testers, sources })` (`input/pointer-router.ts`) turns each pointing source into a `Ray { origin, dir }` through the active camera (`screenRay`: `camera.screenToWorld` at depth 0 and 1, or 0.5 when the far plane is infinite; no allocation per frame) and keeps, per pointer, the nearest `Hit` over the game's `HitTester`s (`(ray) => Hit | null`; shipped: `planeTester(z)` and `aabbTester(boxes)`, which also covers flat 2D quads; *ws/pick:* `sphereTester(transform, bounds)`, `obbTester(transform, halfExtents)` and `meshTester(transform, positions, indices, target, { bounds, cullBack, stride, offset })` pick against a `Transform`'s 3×4 world matrix read each call, moving the ray into object space (`transformRayInto`), rejecting on the bounds sphere and testing triangles with Möller–Trumbore (`rayTriangle`), CPU side only, allocation-free). It emits `hit`, `hitEnd`, `select` and `secondary` (core `Emitter`). Sources implement `PointerSource { poll(camera) => PointerSample[]; attach?; detach? }`: `ScreenPointers` (mouse and pen hover; a touch is a pointer while down plus one tail tick, and a single touch aims through the magnify `aim`) is built in, and `PadCursor` is a stick-driven cursor clamped to `camera.screen`. `input.setPointers(router)` links it like gestures (shared `blocked()`, transform, attach, polled in `Input.update()`), and adds the binding kinds `{ pointer: 'select' | 'secondary' }` and `{ xr: 'trigger' | 'squeeze' | 'pinch', hand? }`. When the input binds the router's `selectAction` (default `select`), a press of that action from any binding selects the primary pointer's hit; otherwise each pointer's button edge does. While blocked every hit ends and nothing selects. *Today (ws/look):* `Look` (`input/look.ts`) reports per tick `look` (yaw/pitch delta, radians), `move` (x, y in -1..1) and `zoom` (positive closer; from the wheel, a pinch beside a look drag and an opted-in pad control, ws/look-zoom) from pointer-locked mouse (`request()`/`release()`, `locked`, `onLockChange`), a two-zone touch layout (a floating move stick in one half, look drags elsewhere), the pad's sticks and named move keys; `input.setLook(look)` links it like gestures (shared `blocked()`, which zeroes it and releases the lock; attached by `Input.attach`; advanced in `Input.update()`), and `createGame` builds none. *Today (ws/follow, E-015):* `Follow` (`input/follow.ts`) is the third-person camera over `Look`: it follows a `target`, orbits from the look deltas with pitch limits, a shoulder offset and a smoothed pivot, calls the game's `obstacle(from, to, outHit)` to swing in on walls, zooms by steps (and from the linked `Look`'s `zoom` axis), and `mode = 'first'` makes it a first-person camera at `eyeHeight` with the same yaw and pitch; it drives the `Camera` only through `lookAt`, allocation-free. *Today (ws/xr):* `XrPointerSource(session, referenceSpace, frame, opts?)` in `input/xr-source.ts` implements `PointerSource` from `XRInputSource.targetRaySpace` per source, with `select = trigger || pinch`, `secondary = squeeze`, trigger and squeeze from the gamepad buttons or the select/squeeze events, pinch from the index-tip to thumb-tip joint distance in metres with hysteresis (`pinchStart` 0.02, `pinchEnd` 0.035) and `x`, `y` NaN; nothing in the router changed. `createGame` builds the router, exposes `ctx.pointers`, and on `ctx.xr.enter()` adds the XR source (removed on exit). *Today (ws/input-replay):* `Input.onFeed(hook)` lets `createInputRecorder` write down every feed call and the pad snapshot per `update()` as a plain-JSON `InputRecording` (deltas only, idle ticks as runs) and `createInputPlayback` feed it back with the recorded pads substituted, so an identical game sees identical action states per tick; `createGame({ input: { record } })` and `{ input: { replay } }` (no DOM listener, `playback.step()` before each fixed step) wire them, and `harness/replay.html` proves record → replay equality on the matrix.

**Layout.** One overlay, laid out in CSS px on every form factor (ws/one-overlay, D-044). A `LayoutSpec` names regions (`top`, `left`, `right`, `bottom`, `cardLane`, `captionLane`, `modal`) per form factor (`phone-landscape`, `phone-portrait`, `tablet`, `desktop`), with safe areas. Games register widgets against regions and the engine places them with CSS grid. The layout reports the free rect, so the world can frame into what the UI leaves. Density tokens `--tc-text-min`, `--tc-tap-min` and `--tc-text-scale` replace the game's `--lr-*` variables. *Today:* `createOverlay` in `ui/overlay.ts` builds one `.tc-overlay` root over the whole parent (letterbox bars included), with no transform, and its layout (`overlay.layout`; `ctx.ui.layout` in a game). Layers, bottom to top: `hud` and `captions` sit on the **frame** (the canvas rect, `--tc-frame-x/y/w/h`, set by `setFrame` on every resize) and clip to it; `layout` covers the whole root; `panels` and `toasts` sit on the frame in `frame` units and cover the root in `css` units. Each form's `FormSpec.units` picks the units (`data-units` on the root, `overlay.units`): `frame` (desktop, tablet) sizes the base UI in design px of the 1920×1080 frame, `--tc-dpx` CSS px each, so it keeps its proportions to the canvas; `css` (phones) takes `cssPxTheme` sizes as CSS px. `--tc-unit` is what one px of a design-px stylesheet draws as on each layer: `--tc-dpx` on the frame's layers, 1px in the regions and, in `css` units, in panels and toasts. `toFrameUnits(css)` (in `ui/text-scale.ts`) rewrites a design-px sheet's `Npx` to `calc(N * var(--tc-unit, 1px))`; games pass their sheets through it and `scaleFontSizes`. World-anchored DOM (labels over 3D objects) goes in `hud` at its design coordinates times `--tc-unit` (the same point as `surface.logicalToClient`), so it follows every resize without JS. Native controls whose parts are CSS px (range thumbs, select arrows) are zoomed by `--tc-zoom` (the scale as a number) on the frame's layers. `createLayout(overlay, spec?)` in `ui/layout.ts` (internal; `createOverlay` calls it with `OverlayOptions.layout`) classifies the form factor (`phone-landscape`, `phone-portrait`, `tablet`, `desktop`: a phone is a coarse pointer with a short side of at most 600, or any view under 480), resolves each form's px tracks and grid areas inside the safe area (`env(safe-area-inset-*)`, overridable with `--tc-safe-*` or `setSafeArea`), collapses tracks whose regions have no widgets, and draws the same px grid in the DOM. `layout.add(el, { place: { default, <formFactor> } })` moves a widget between regions on an orientation change; `'hidden'` hides it; `{ region: 'free', rect, reason }` is the escape hatch (logged once with `console.info` and listed in `freeUses`); `WidgetHandle.remove()` puts an element back where it was before `add`. `layout.freeRect` is the `fill` region, the space the world gets; `onChange` reports every re-layout. `layout.setForms(forms | null)` lays a scene's own tracks over the spec's, per form factor and field by field, for regions that follow the scene's content; the scene sets it on enter and on resizes and clears it on exit. `layout.dockCaption()` moves the caption card into `captionLane` (`caption.dock(host)`); undocked, the card sits in a frame corner and a game steers it with `caption.onPlace` and `caption.relayout()`. The layout owns `--tc-tap-min` (44 on touch forms), `--tc-text-min`, `--tc-region-pad`, `--tc-safe-*-px` and `--tc-modal-*`; buttons, toggles, sliders and panels honour them. `--tc-text-scale` and `scaleFontSizes` are in `ui/text-scale.ts`; `platform/device-mode.ts` (`data-phone`, `data-touch`) and `ui/rotate-card.ts` are interim API; the phone stylesheets stay in the game (`ui/phone-base.ts` and each scene's `*-phone-styles.ts`). `device`, `setFill(key)` and the fill bands are gone (ws/render-call, E-010): a 2D game fits its camera to `freeRect` with `Camera.fitFreeRect(worldRect, freeRect, surface)`, which does the CSS-px conversion itself (ws/plumbing). In a region's flex box `top` and `bottom` are rows (`ui/README.md`).

See CHANGELOG.md, "Removed (ws/one-overlay)".

Debug draw (`fx/debug-draw.ts`, ws/debug-draw) is a `Drawable` that appends world-space line segments (xyz + rgba vertices) for wire boxes, spheres, axes, arrows, rays, grids, circles, paths and frustums into one CPU array, uploads the used range once and draws it as a single 1 px `'line-list'` with a pipeline per `frame.depthFormat`, depth tested (never written) or `depth: 'always'` for overlays, clearing after each draw unless `retain`. Billboards (`fx/billboard.ts`, ws/billboards) draw world-anchored quads (name plates, damage numbers, health bars) as one storage-buffer instanced batch, sized in world units or in screen px from the camera block's `viewport`, textured from a shelf-packed, LRU-evicting canvas `TextAtlas` uploaded once per frame when dirty, sorted back to front and alpha blended over the depth buffer without writing it.

**Localisation.** `i18n/` (ws/i18n) ships a game in several languages with no dependency and no network: `createI18n({ locale, fallback, tables, missing, onMissing })` holds one string table per locale, inline or behind a loader the game supplies (`() => import('./ru.json')`), parses every string once into an AST per dotted key (ICU-style `{name}`, `{n, plural, …}` with `Intl.PluralRules`, `=N` forms and `#`, `{g, select, …}`, `{n, number}`, `{d, date}`; errors name the key and column) and formats on `t(key, args)` allocating only the output string, looking the key up along a chain (the locale, its language, each fallback) and pluralising with the rules of the table the string came from. `setLocale` loads what the new chain needs (one pending promise per locale, the latest call wins) and then notifies `subscribe` callbacks, which is how a menu or HUD re-renders; `direction` is `'rtl'` for a small RTL language set and the store never touches the DOM. Numbers, dates, durations and lists go through cached `Intl` objects (`formatNumber`, `formatDate`, `formatDuration`, `formatList`). `negotiateLocale(available, requested = navigator.languages)` picks the table for a browser (exact, then language, then the fallback). Nothing in the engine imports `i18n`; `ui` may later. *Planned:* a `ui` binding that re-renders widgets from keys.

**Assets.** File formats become engine objects here, from bytes the game fetched (VISION rule 4: no network call in the engine). *Today:* glTF 2.0 geometry, skins and animations in `assets/`. `parseGltf(bytes | { json, buffers })` reads `.glb` and `.gltf` (data: URIs decoded, external URIs listed in `externalUris`) into an engine-free `GltfDocument`: per primitive position, normal (flat when absent), uv0, color0, indices (generated when absent) and bounds; per node TRS and 3×4 local and world matrices; per material base colour factor and texture, alpha mode and cutoff; per image bytes or uri. `loadGltf(renderer, doc, opts?)` makes one `Mesh` per primitive in `VERTEX_LAYOUT_3D` (with the primitive's bounds as `MeshDesc.bounds`, so `camera.cull` skips it), one `Transform` per node, one sRGB mipmapped `Texture` per image and one lit `Material` per glTF material (or the one `opts.material`), and the `GltfScene` draws them with `frame.mesh` per node without allocating. Sparse accessors outside morph targets, non-triangle modes and `extensionsRequired` throw `GltfError`. Skins and animations parse into the animation module's shapes without a converter: `doc.skins` (joints, 3×4 inverse bind rows), `doc.animations` as `AnimationClip`s (every interpolation, cubic-spline tangents kept), `primitive.joints`/`weights`, `interleaveSkinned` for the skinned vertex layout and `skeletonFromSkin` for a `Skeleton` with the rest pose from node TRS. Morph targets (ws/morph): `primitive.targets` (`POSITION` and `NORMAL` deltas per target, dense or sparse over zeros or a dense base; other target attributes listed in `ignoredTargetAttributes`) and `mesh.weights` parse; `loadGltf` keeps the base vertex buffer only for primitives with targets, blends them through `anim`'s `createMorphBlender` behind `scene.morph(nodeIndex)` (`GltfMorph`: one weights array per mesh, `apply()`), and `draw` uploads changed primitives with `Mesh.update`. A typed manifest (`defineManifest`) loads through `createBundle` from the game's `read(uri)` with bounded, prioritised, deduplicated reads, progress in assets and bytes, per-key errors, cancel and release, and `packAtlas` / `createAtlasTexture` shelf-pack sprites into one texture with extrusion and uv rects. *Planned:* `KHR_texture_transform` and the `KHR_materials_*` family.

**Analytics.** Typed, batched game events handed to a sink the game supplies; the engine makes no network call (VISION rule 4). *Today:* `createAnalytics<E>({ sink, session?, clock?, context?, onError?, maxBatch? })` in `analytics/` returns `emit(name, props)`, `flush()` and `attach(ctx)`. Each event carries `name`, `props`, a per-page-load `session`, a monotonic `seq` and `t`. `attach` emits `game_start` (form factor, host kind, DPR, viewport, embed, build), wraps `ctx.hooks.hide`, `show` and `deviceLost` (the game's hooks still run), emits `device_lost`, and on `hooks.hide(reason)` (hidden, pagehide, freeze) or device loss emits `session_end` with that reason and flushes; `show` re-arms it. It adds no lifecycle listeners of its own. A failing sink goes to `onError`; `emit` and `flush` never throw. `templates/puzzle` shows the conventions (ws/plumbing): a `navigator.sendBeacon` sink (`createBeaconSink(url)` in `templates/puzzle/src/analytics.ts`) and `level_start` / `level_complete` events.

**Geometry.** Shapes are arithmetic the game can call for, not files it must ship: a `Geometry` (`vertices`, `indices`, `bounds`, `layout`) is a `MeshDesc`, so `renderer.createMesh(geometry)` takes it as it is. *Today (ws/geom):* `@thunderclap/engine/geom` (`geom/`) is pure TypeScript whose only `render/` imports are types. The builders `box`, `plane`, `sphere` (UV), `icosphere`, `capsule`, `cylinder` (and cones) and `torus` take sizes, segment counts, a `color` and a `uvScale`, and return `VERTEX_LAYOUT_3D` geometry wound counter-clockwise from outside with unit normals, flat where the surface is (box, plane, cylinder caps) and smooth where it is not; indices are 16-bit until a geometry passes 65535 vertices, then 32-bit. `Heightfield { width; depth; heights; scale; origin }` with `heightAt` (bilinear), `normalAt`, `raycastHeightfield` (a DDA over the cells the ray crosses, each cell's bilinear patch solved exactly, no allocation; the distance or -1) and `heightfieldGeometry` (smooth or flat). `mergeGeometry` concatenates parts and offsets their indices, `transformGeometry` applies a 3×4 world matrix to positions and its inverse transpose to normals, and `GeometryWriter` is the hand-built path the builders use. The second half (ws/geom-2) adds sweeps over a 2D `Profile2D` (`extrude` with bevelled ear-clipped caps, `lathe`, `sweep` and `tube` along a polyline with rotation-minimising frames, `polygon`, `stairs`, `arch`), `computeTangents` (MikkTSpace-style accumulation, orthonormalised, handedness in `w`) into `VERTEX_LAYOUT_3D_TANGENT` (the 3D layout plus `tangent: vec4f` at `@location(13)`, 16 floats), and the operations `flatShade`, `weld`, `flipWinding`, `projectUv`, `fitBounds` and `recenter`.

**Scene and Ctx.** `Scene<Ctx, Frame, Cam>` and `SceneStack` are in `core/`. *Today:* `createGame(opts)` in `core/game.ts` (exported from the root entry `@thunderclap/engine`, not `./core`, because it is the top layer and pulls in every module) builds the engine's ctx and resolves to `EngineCtx`, or to `null` when WebGPU is missing (the unsupported screen is shown). It blocks browser zoom (double-tap, pinch, ctrl+wheel; option `blockBrowserZoom`, default on), boots the letterboxed surface, and builds the renderer, post stack, particles, host, save (`opts.save(host)`, opt-in), overlay, pad nav, audio (with `persistMixer` when `mixerKey` is set), input (blocked under a modal) with its gestures (`new Gestures({ magnify: opts.input.magnify })`) and its pointer router (`createPointerRouter({ camera: () => renderer.camera })`), both passed to the `Input` constructor so they share its block, transform and attach. It wires resize (renderer, the overlay's frame via `ui.setFrame`, which re-lays the layout), the loop (frames from `host`; input → pad nav → `hooks.update` → particles → scenes, in fixed steps of `sim.step`, default 1/60; `hooks.beforeRender` → `renderer.beginFrame` → `stack.render(frame, ctx.camera, alpha)` → `renderer.render(frame, ctx.camera)` → `renderer.endFrame()` → `hooks.afterRender` → `ui.updateAnchors()`; while an XR session runs, the scenes record once through `xr.surface.head`, each eye renders into `xr.surface.scene` and `renderer.resolve` runs the post stack into the eye's part of the layer, and `endFrame({ present: false })` submits), page lifecycle (hidden, pagehide, freeze: stop the loop, `hooks.hide(reason)` with `HideReason` `'hidden' | 'pagehide' | 'freeze'`, flush the save; shown: resume the loop, then `hooks.show(reason)`, unless the device was lost) and device loss (boot shows the reload screen, then: halt the loop for good, `hooks.deviceLost`, halt audio, suspend the caption, flush). Two parts are opt-in so a pure client of a server-authoritative game (VISION pillar 6) boots through the same call: **save**: without `opts.save`, `S` is `null`, `ctx.save` is `null` (typed `null`; such a ctx is not assignable to `EngineCtx<A>`, whose default `S` is `FlushableSave`, and `createGame` does not infer `S` from a return annotation), hide and device loss flush nothing, and nothing reads `host.storage` (leave `mixerKey` out too); **sim**: `opts.sim: false` runs the loop at render rate (`GameLoopOptions.fixed: false`), so input → pad nav → `hooks.frame(dt)` → particles → scenes' `update(dt)` run once per rendered frame with the real delta and `hooks.update` never runs. Callers that pass `save` and no `sim` get exactly the old behaviour. The harness's `game.html?mode=client` boots that way (e2e/client.spec.ts). `EngineCtx<Action, Save, Ctx>` (`Save extends FlushableSave | null`) holds `design`, `surface`, `gpu`, `renderer`, `camera` (the renderer's default `Camera`, the one the scenes draw through; re-aimed in place), `post`, `particles`, `input`, `gestures` (the `Gestures` linked to `input`), `padNav`, `audio`, `ui` (the one overlay, with its layout as `ui.layout`; `CreateGameOptions.layout` is its `LayoutSpec`), `host`, `pointers` (`PointerRouter<unknown>`), `xr` (`XrControl`, always present: `supported()`, `enter()`, `exit()`, `active`, `session`, `surface`; `CreateGameOptions.xr` only tunes it, ws/xr), `save`, `stack`, `loop`, `hooks` and `onDeviceLost(fn)`. A game widens that same object with its nouns (`Object.assign(engine, {...})`), so scenes get one ctx; Last Rune's `GameCtx extends EngineCtx` in `games/last-rune/game/ctx.ts` (in the game repo, not here). `templates/puzzle` is a copyable game: pure `rules/`, a versioned save schema with one migration, a layout spec, a scene on `frame.sprite` + `Transform`, and a `CLAUDE.md` naming the engine concepts. `device`, `setFill(key)` and `CreateGameOptions.fillBands` are gone (ws/render-call, D-044): a 2D game frames `ui.layout.freeRect` with `ctx.camera.fitFreeRect(worldRect, ui.layout.freeRect, surface)`, which the template does on enter and every re-layout; the template also shows the analytics convention (`createBeaconSink(url)` in `templates/puzzle/src/analytics.ts`, `level_start` / `level_complete`). The layout stays on `ui`. *Planned:* the fixed pipeline (post, particles, audio, pad nav, loop order) opens up when a game needs it.
