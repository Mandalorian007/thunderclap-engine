# ThunderClap engine: architecture and contracts

`@thunderclap/engine` is the WebGPU engine The Last Rune is built on. It knows nothing about any game. This file is the target the PM reviews promotions and public API changes against (D-041, [refactor plan](https://github.com/Mandalorian007/last-rune/blob/main/docs/engine/refactor-plan.md)). Decision numbers (D-0xx) and `docs/` paths in this repo refer to [The Last Rune](https://github.com/Mandalorian007/last-rune), where the engine was built. Each contract says what exists **today** (0.2.0-dev) and what is **planned**, with the phase that delivers it.

## Package shape

```
thunderclap-engine/
  package.json        # @thunderclap/engine; the "exports" map is the public API
  src/
    index.ts          # the "." entry: createGame and its types
    audio/  core/  fx/  host/  input/  platform/  post/  render/  save/  ui/
  harness/            # noun-free e2e pages: index.html boots the platform layer (window.__harness);
                      # game.html boots through createGame (window.__harnessGame); ui.html is DOM only
  e2e/                # engine e2e specs, fixtures, ports, itch-style iframe wrapper
  playwright.config.ts  # the viewport/device/wrapper matrix every engine spec runs on
  ARCHITECTURE.md     # this file
  CHANGELOG.md
```

**Test ownership (D-041 addendum 2).** The engine verifies platform capability once, for every game: unit tests (`src/**/*.test.ts`, Vitest) and e2e specs (`e2e/`, Playwright) run against the `harness/` page. Every spec runs on the whole matrix in `playwright.config.ts`: desktop 1280×720 and 1920×1080, iPad 1180×820, four phones (667×320, 844×340, 932×380, 915×360, touch at DPR 2), and the harness inside an itch-style cross-origin iframe. Two upright rows, `phone-port` 390×844 and `tablet-port` 820×1180, run the layout spec only. A new platform capability (host, gestures, layout, lifecycle) adds a probe to the harness and a spec here, not in a game. Games test product only.

Games import only the exports map: `@thunderclap/engine` (the `"."` entry: `createGame` and its types) and `@thunderclap/engine/<module>` for `audio`, `core`, `fx`, `host`, `input`, `platform`, `post`, `render`, `save` and `ui`, plus `@thunderclap/engine/testing` (the recording fake `GPUDevice`, for unit tests only). Each subpath is that module's `index.ts`; anything not re-exported there is internal. `pnpm check:boundaries` (`scripts/check-boundaries.mjs`, part of `pnpm check`) fails if a game, test or script imports a path outside the map or reaches into `packages/engine/` by a relative path, or if anything under `src/` imports a game. Inside the package, modules import each other by relative path.

The package ships TypeScript source; the game's Vite build compiles it. There is no separate engine build until Phase 5 (extraction and publishing).

## Ground rules

1. **Promotion rule.** Code enters the engine only if Last Rune uses it, the next game plausibly would, and its API has zero game nouns.
2. **Dependency direction.** `games/*` imports `@thunderclap/engine`; the engine never imports a game. A game's `rules/` imports nothing from the engine or the DOM.
3. **No runtime dependencies** without a DECISIONS entry (D-008). WebGPU is the only renderer.
4. **Seams, not features.** 3D content and XR are out of scope until after Gate 5. The engine grows the three seams they would plug into (`Surface`, `Camera`, the frame loop) and nothing else on speculation.

## Contracts

**Surface.** Owns the canvas, the swapchain, DPR, the backbuffer size and the letterbox or fill-width fit. It exposes `rect` (CSS px), `size` (device px), `clientToLogical` and `onResize`. Later an `XRSurface` provides a target per eye per frame through the same interface. *Today:* `Surface` / `mountSurface` in `platform/surface.ts` exposes `rect`, `backbuffer` (device px; the planned name is `size`), `clientToLogical`, `logicalToClient`, `onResize`, `setFill` (fill-width) and `setFrame(rect | null)` (letterbox inside a part of the container, CSS px, e.g. the layout's `freeRect`), over the pure letterbox math in `platform/letterbox.ts`; `initGpu` configures the swapchain. *Planned:* the `size` rename and the target-per-frame shape arrive with Phase 3's `render(camera, target)`; `XRSurface` is after Gate 5.

**Camera.** A view-projection matrix plus `worldToScreen` and `screenToWorld` (the inverse projection; touch aiming uses it). Presets: `ortho2d(designW, designH)`, where 1 unit = 1 design px, and `fitRect(rect, viewport)`, which fits a world rect into a viewport. Depth test and depth write are camera-preset flags; the 2D preset leaves both off. *Today:* `render/renderer.ts` has a 2D `Camera` (`x`, `y`, `zoom`, `rotation` over the logical space) read from `renderer.camera`. The renderer also reads three optional draw-list fields from that object (ws/transforms): `layers` (u32 mask; missing = every layer; draws with `layers & camera.layers === 0` are skipped), `depthTest` (default off: no depth attachment, draws sorted by `order` then submission) and `depthWrite` (default on when `depthTest` is set), plus `position` (xyz) for depth sorting. *Planned:* Phase 3 (ws/camera) adds the matrix `Camera`, `mat4` in `core/math.ts` and the camera uniform block, and gives `layers`, `depthTest`, `depthWrite` and `position` their typed home on it; the clip-position line in `engine_vertex` then uses the instance's world z.

**Transforms, layers and instances.** Every draw is one 28-float instance whose placement is a 3×4 world matrix, so 2D sprites, meshes and later voxels share one vertex path. *Today:* `render/transform.ts` exports `Transform` (position xyz, rotation about Z for 2D as `rotation` in radians, or any 3D rotation as a unit quaternion via `setQuaternion` / `setAxisAngle`; scale xyz; optional `parent`) with a cached 3×4 row-major `world` matrix that recomputes only when it or an ancestor changes. `frame.sprite(mat, DrawParams)` still works and writes the matrix directly (`writeMatrix2d`, exact at rotation 0, no allocation); `frame.sprite(mat, transform, params?)` and `frame.mesh(mesh, mat, transform, params?)` take a `Transform`. Every draw carries `layers` (u32, default 1) and `order` (sort key, default 0). Without depth, draws sort by `order` then submission index, so the default reproduces submission order and batching exactly. With `camera.depthTest`, keys are `order`, then opaque before blended, then distance (opaque front-to-back, blended back-to-front), then submission index; the depth24plus attachment is allocated only then. Meshes carry a `VertexLayout`: `VERTEX_LAYOUT_2D` (8 floats, unchanged; `quadGeometry()` unchanged) or `VERTEX_LAYOUT_3D` (xyz, normal xyz, uv, rgba = 12 floats). Materials build pipelines lazily per (vertex layout, depth mode) from a per-layout prelude (`materialPrelude(layout)`), so a game's `fs_main` is unchanged. *Planned:* drawables (particles) gain depth-aware pipelines when a depth camera needs them; instance `flags` (float 25) are reserved.

**Frame loop.** `GameLoop` as today (fixed 60 Hz update, variable render), but `render(camera, target, alpha)` takes the camera and the target as inputs instead of reading them from the renderer. The host decides who schedules frames (rAF, Electron, later `XRSession.requestAnimationFrame`). *Today:* `GameLoop` and `FixedStepper` in `core/loop.ts` (fixed step, `maxFps` cap, pause) call `render(alpha, time)` from `requestAnimationFrame`; `Scene<Ctx, Frame>` and `SceneStack` in `core/scene.ts`. *Planned:* the `render(camera, target, alpha)` signature in Phase 3 (ws/render-call); host-owned scheduling with the host layer.

**Host.** `interface Host { kind; openExternal; copyText; fullscreen; storage; window?; embed }`. Implementations: `web` (detects iframe vs top and wraps today's D-036 link service) and `electron` (preload bridge). After Phase 1 the engine never calls `window.open`, `navigator.clipboard` or `localStorage` directly. *Today:* `host/` (`@thunderclap/engine/host`) has the `Host` type, `createWebHost({ win? })` and `defaultHost()` / `setDefaultHost()`. The web host also exposes `clipboardWriteAllowed()`; `fullscreen` is `{ available, active, toggle, watch }` and `storage` is `{ kind, open(): StorageLike | null }`. `save` (`createSaveStore`, `listSlots`), `persistMixer` and the `externalLink` widget take `host` and default to `defaultHost()`. `window.open`, `navigator.clipboard`, `execCommand` and `localStorage` appear only in `host/web.ts` and `host/web-links.ts`; the fullscreen DOM calls stay in `platform/device.ts`, which the web host wraps. Phase 4 (ws/host-electron) adds `createElectronHost()` in `packages/host-electron` (`@thunderclap/host-electron`): the same interface over the preload bridge `window.thunderclap`, `kind: 'electron'`, storage the renderer's `localStorage` (served from the fixed origin `app://bundle`), and `window` with `close`, `minimize`, `toggleMaximize` and `setTitle`. A game installs it with `setDefaultHost` or passes it to its ctx; the engine never imports it. *Planned:* `Host.requestFrame` (rAF on web and Electron, `XRSession.requestAnimationFrame` later), so XR is a `Host` implementation, not a redesign; `GameLoop` takes its frame source from it (ws/render-call, D-044).

**Input.** The action map for keyboard, mouse, touch, pen and gamepad, with `blocked()`, `lastDevice`, queued taps, iframe-safe `preventDefault`, injectable pads and public feed methods for tests; `ui/padnav.ts` drives modal panels from the pad and `ui/menu-nav.ts` (`menuNav`) drives non-modal menus. `Gestures` (`input/gestures.ts`) recognises tap, double tap, long-press (450 ms), pan, drag (with its origin) and pinch (scale) from pointer events, with thresholds in CSS px (pan 10) and positions in game space through the same `PointerTransform`. It reports per tick like `Input`: one discrete gesture per kind per tick (extras queue), continuous ones every tick from `start` to `end` or `cancel`. `input.setGestures(g)` links it: the gestures share `blocked()` and the transform, attach with `Input.attach`, advance in `Input.update()`, and can be bound as actions (`{ gesture: 'tap' | 'doubleTap' | 'longPress' | 'pan' | 'drag' | 'pinch' }`), so a game can map tap to `select` and long-press to `info` without reading gestures. While blocked nothing is reported and a running pan, drag or pinch gets one `cancel`. The `magnify` option (`input/magnify.ts`, ws/port-altar) is loupe and snap for small touch targets: while one touch pointer is down each tick reports `gestures.aim`, the finger raised by `lift` (56 CSS px) while it drags, snapped by the game's `snap(x, y)` (usually `snapToGrid`, the nearest accepted cell within half a pitch), and while `pitch()` is below `below` (44 CSS px) a `Loupe` beside the finger magnifies the aim point `zoom` (2.5) times with the target ringed. The aim the finger lifted at is reported once more (`ended`) on the drag's `end` tick, so a dragged thing lands where it was aimed. Mouse and pen never aim.

**Layout.** `createOverlay` laid out in CSS px, not design px. A `LayoutSpec` names regions (`top`, `left`, `right`, `bottom`, `cardLane`, `captionLane`, `modal`) per form factor (`phone`, `tablet`, `desktop`, each in `landscape` or `portrait`), with safe areas. Games register widgets against regions and the engine places them with CSS grid. The layout reports the free rect to the camera, so the world frames into what the UI leaves. Density tokens `--tc-text-min`, `--tc-tap-min` and `--tc-text-scale` replace the game's `--lr-*` variables. *Today:* `createOverlay` in `ui/overlay.ts` defaults to `legacyScale: true`, a 1920×1080 design canvas shrunk by one CSS `scale()` transform, with layers for hud, captions, panels and toasts; every game scene still uses it. `createOverlay({ legacyScale: false })` is the CSS-px mode (`data-units="css"`, the root is the surface rect in CSS px, `cssPxTheme` sizes). `createLayout(overlay, spec?)` in `ui/layout.ts` runs on a CSS-px overlay only. It classifies the form factor (`phone-landscape`, `phone-portrait`, `tablet`, `desktop`: a phone is a coarse pointer with a short side of at most 600, or any view under 480), resolves each form's px tracks and grid areas inside the safe area (`env(safe-area-inset-*)`, overridable with `--tc-safe-*` or `setSafeArea`), collapses tracks whose regions have no widgets, and draws the same px grid in the DOM. `layout.add(el, { place: { default, <formFactor> } })` moves a widget between regions on an orientation change; `'hidden'` hides it; `{ region: 'free', rect, reason }` is the escape hatch (logged once with `console.info` and listed in `freeUses`). `layout.freeRect` is the `fill` region, the space the world gets; `onChange` reports every re-layout. `layout.setForms(forms | null)` lays a scene's own tracks over the spec's, per form factor and field by field, for regions that follow the scene's content (a board sized first, a column taking what is left); the scene sets it on enter and on resizes and clears it on exit. `layout.dockCaption()` moves the caption card into `captionLane` (`caption.dock(host)`); the legacy `avoid()` path is unchanged. The layout owns `--tc-tap-min` (44 on touch forms), `--tc-text-min`, `--tc-region-pad`, `--tc-safe-*-px` and `--tc-modal-*` on a CSS-px root, and `device-mode` leaves them alone there; buttons, toggles, sliders and panels honour them. `--tc-text-scale` and `scaleFontSizes` are in `ui/text-scale.ts`; `platform/device-mode.ts` and `ui/rotate-card.ts` are interim API for legacy scenes; the phone stylesheets stay in the game (`ui/phone-base.ts` and each scene's `*-phone-styles.ts`). *Planned:* ws/one-overlay (the Phase 3 entry condition, D-044) moves `ctx.ui` to CSS px on every form factor and deletes `avoid()`, `legacyScale` and `createCssChrome`; ws/camera then feeds `freeRect` to `Camera.fitRect`.

**Two overlays (ws/port-chrome).** A game ports its scenes to regions one form factor at a time, so for a while two overlays coexist. `createGame({ overlay: { layout, cssForms } })` builds `ctx.chrome` with `createCssChrome` (`ui/css-chrome.ts`); without the option `ctx.chrome` is null and nothing changes. `ctx.ui` stays the legacy scaled overlay over the canvas rect and keeps the one `PanelStack`, `Toaster` and `CaptionCard`, so pad navigation, input blocking under a modal and caption suspension are unchanged. `chrome.ui` is a second, CSS-px overlay (`data-units="css"`, `data-form-factor`) over the whole container, letterbox bars included, stacked above the legacy one, with `chrome.layout` on it. Its own stack, toasts and caption stay idle. `chrome.active` is true while the layout's form factor is in `cssForms` (default: both phone forms; a game can sharpen the boundary with `LayoutSpec.classify`). While active, the legacy overlay's `panels` and `toasts` layers move into `chrome.ui.root`, so every panel and toast lays out in CSS px with the layout's tokens and modal region. While inactive they are back in the legacy root and `chrome.ui.root` is hidden, so a desktop or tablet frame is identical to a game without the option. Scenes add their widgets with `layout.add()` and dock the legacy caption with `layout.dockCaption(ctx.ui.caption)`; `WidgetHandle.remove()` puts an element back where it was before `add` (a detached element is removed). World-anchored DOM (labels over 3D objects) stays on the legacy overlay, because it follows the canvas transform. To frame the world into what the regions leave, a scene calls `surface.setFrame(layout.freeRect)`; `setFrame(null)` restores the full container.

**UI, Audio, Save, FX, Post.** The APIs are unchanged; the overlay's scaling model is the one change inside UI. *Today:* `ui/` (overlay stack, panels, widgets, toasts, captions, loupe, external-link widget, theme tokens), `audio/` (WebAudio buses, synth, recipes, mixer persistence), `save/` (versioned slots, migrations, quota- and blocked-storage-safe), `fx/` (GPU particles, flicker) and `post/` (bloom, god rays, fog, vignette, grade, quality tiers). Each module has a README with usage. `save` takes its storage from the host (`host.storage`).

**Scene and Ctx.** `Scene<Ctx, Frame>` and `SceneStack` are in `core/`. *Today:* `createGame(opts)` in `core/game.ts` (exported from the root entry `@thunderclap/engine`, not `./core`, because it is the top layer and pulls in every module) builds the engine's ctx and resolves to `EngineCtx`, or to `null` when WebGPU is missing (the unsupported screen is shown). It blocks browser zoom (double-tap, pinch, ctrl+wheel; option `blockBrowserZoom`, default on), boots the letterboxed surface, and builds the renderer, post stack, particles, host, save (`opts.save(host)`), overlay, pad nav, device mode, audio (with `persistMixer` when `mixerKey` is set) and input (blocked under a modal). It wires resize (renderer, overlay rect, phone scale, fill bands), the fixed-step loop (input → pad nav → `hooks.update` → particles → scenes; `hooks.beforeRender` → scenes → `hooks.afterRender`), page lifecycle (hidden, pagehide, freeze: stop the loop, `hooks.hide`, flush the save; shown: resume) and device loss (halt the loop for good, `hooks.deviceLost`, halt audio, flush, reload screen). `EngineCtx<Action, Save, Ctx>` holds `design`, `surface`, `gpu`, `renderer`, `post`, `particles`, `input`, `padNav`, `audio`, `ui`, `chrome` (the CSS-px overlay, or null; see "Two overlays"), `host`, `device`, `save`, `stack`, `loop`, `hooks`, `setFill(key)` and `onDeviceLost(fn)`. A game widens that same object with its nouns (`Object.assign(engine, {...})`), so scenes get one ctx; Last Rune's `GameCtx extends EngineCtx` in `games/last-rune/game/ctx.ts`. *Planned:* `camera`, `layout` and `gestures` join `EngineCtx` in Phases 2 and 3. `device` and `setFill(key)` (with the fill bands) are interim phone concepts; ws/camera deletes them in favour of `layout.freeRect` and `Camera.fitRect` (D-044). The fixed pipeline (post, particles, audio, pad nav, loop order) opens up in ws/render-call.
