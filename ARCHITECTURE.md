# ThunderClap engine: architecture and contracts

`@thunderclap/engine` is the WebGPU engine The Last Rune is built on. It knows nothing about any game. This file is the target the PM reviews promotions and public API changes against (D-041, [refactor plan](https://github.com/Mandalorian007/last-rune/blob/main/docs/engine/refactor-plan.md)). Decision numbers (D-0xx) and `docs/` paths in this repo refer to [The Last Rune](https://github.com/Mandalorian007/last-rune), where the engine was built. Each contract says what exists **today** (0.2.0-dev) and what is **planned**, with the phase that delivers it.

## Package shape

```
thunderclap-engine/
  package.json        # @thunderclap/engine; the "exports" map is the public API
  pnpm-workspace.yaml # packages: ['packages/*']; the engine stays the root package
  packages/
    host-electron/    # @thunderclap/host-electron: the Electron shell (main, preload) and
                      # createElectronHost(); depends on the engine via "workspace:*" (links the root)
  src/
    index.ts          # the "." entry: createGame and its types
    audio/  core/  fx/  host/  input/  platform/  post/  render/  save/  ui/
  harness/            # noun-free e2e pages: index.html boots the platform layer (window.__harness);
                      # game.html boots through createGame (window.__harnessGame); ui.html is DOM only
  e2e/                # engine e2e specs, fixtures, ports, itch-style iframe wrapper
  playwright.config.ts  # the viewport/device/wrapper matrix every engine spec runs on
  ARCHITECTURE.md     # this file
  CHANGELOG.md
```

**Test ownership (D-041 addendum 2).** The engine verifies platform capability once, for every game: unit tests (`src/**/*.test.ts`, Vitest) and e2e specs (`e2e/`, Playwright) run against the `harness/` page. Every spec runs on the whole matrix in `playwright.config.ts`: desktop 1280×720 and 1920×1080, iPad 1180×820, four phones (667×320, 844×340, 932×380, 915×360, touch at DPR 2), and the harness inside an itch-style cross-origin iframe. Two upright rows, `phone-port` 390×844 and `tablet-port` 820×1180, run the layout spec only. A new platform capability (host, gestures, layout, lifecycle) adds a probe to the harness and a spec here, not in a game. Games test product only.

Games import only the exports map: `@thunderclap/engine` (the `"."` entry: `createGame` and its types) and `@thunderclap/engine/<module>` for `audio`, `core`, `fx`, `host`, `input`, `platform`, `post`, `render`, `save` and `ui`, plus `@thunderclap/engine/testing` (the recording fake `GPUDevice`, for unit tests only). Each subpath is that module's `index.ts`; anything not re-exported there is internal. `pnpm check:boundaries` (`scripts/check-boundaries.mjs`, part of `pnpm check`) fails if anything under `src/` imports from outside `src/` or through the package name, or if `harness/`, `e2e/`, `examples/` or `templates/` imports a subpath outside the map or reaches into `src/` by a relative path. Inside the package, modules import each other by relative path. A game, in its own repo, is held to the same map by its own checks.

**Workspace.** The engine is the root package, so a dependency on this repo by URL still resolves to it. `packages/host-electron` is a workspace package that depends on the engine with `"workspace:*"`, which pnpm links to the root. It is self-contained: the root `tsconfig.json` does not include `packages/`, and `pnpm check` runs `check:host-electron` (typecheck, lint, unit tests) after the engine's own checks. Desktop builds go to `dist/desktop/` at the repo root (gitignored). The engine never imports the package.

The package ships TypeScript source; the game's Vite build compiles it. There is no separate engine build until Phase 5 (extraction and publishing).

## Ground rules

1. **Promotion rule.** Code enters the engine only if Last Rune uses it, the next game plausibly would, and its API has zero game nouns.
2. **Dependency direction.** `games/*` imports `@thunderclap/engine`; the engine never imports a game. A game's `rules/` imports nothing from the engine or the DOM.
3. **No runtime dependencies** without a DECISIONS entry (D-008). WebGPU is the only renderer.
4. **Seams, not features.** 3D content and XR are out of scope until after Gate 5. The engine grows the three seams they would plug into (`Surface`, `Camera`, the frame loop) and nothing else on speculation.

## Contracts

**Surface.** Owns the canvas, the swapchain, DPR, the backbuffer size and the letterbox or fill-width fit. It exposes `rect` (CSS px), `size` (device px), `clientToLogical` and `onResize`. Later an `XRSurface` provides a target per eye per frame through the same interface. *Today:* `Surface` / `mountSurface` in `platform/surface.ts` exposes `rect`, `backbuffer` (device px; the planned name is `size`), `clientToLogical`, `logicalToClient`, `onResize`, `setFill` (fill-width) and `setFrame(rect | null)` (letterbox inside a part of the container, CSS px, e.g. the layout's `freeRect`), over the pure letterbox math in `platform/letterbox.ts`; `initGpu` configures the swapchain. `createGame` no longer calls `setFill`: a 2D game frames `ui.layout.freeRect` with `Camera.fitRect` (ws/render-call, D-044); `setFill` and `computeFillWidth` remain in `platform/` for a caller that wants them. *Planned:* the `size` rename; a `SceneTarget` per eye through `renderer.render(frame, camera, target)`; `XRSurface` is after Gate 5.

**Camera.** A view-projection matrix plus `worldToScreen` and `screenToWorld` (the inverse projection; touch aiming uses it). Presets: `ortho2d(designW, designH)`, where 1 unit = 1 design px, and `fitRect(rect, viewport)`, which fits a world rect into a viewport. Depth test and depth write are camera-preset flags; the 2D preset leaves both off. *Today:* `Camera` in `render/camera.ts` (ws/camera) holds `view`, `projection` and `viewProjection` (column-major `Float32Array(16)` from `mat4` in `core/math.ts`, `@thunderclap/engine/core`; cached, recomputed on read after a change), `position`, `depthTest`, `depthWrite`, a `layers` membership mask (u32, default all bits; the draw sort `order` belongs to ws/transforms) and `screen`, the rect clip space spans in the units `worldToScreen` returns and `screenToWorld` takes. `Camera.ortho2d(w, h)` is origin top-left, y down, and looks down +z (right-handed with y down: larger z is farther), spanning world z in ±`ORTHO2D_HALF_DEPTH` (1024; z = 0 sits at clip depth 0.5), with `screen` = the design space; its 2D controls `x`, `y`, `zoom` and `rotation` are the earlier 2D camera's, and its `viewProjection` uses the same arithmetic, so the 2D path is pixel-identical. `fitRect(rect, viewport = screen)` sets those controls (rotation 0) so a world rect is contained and centred in a viewport given in screen units. `Camera.perspective(fovY, aspect, near, far)` is right-handed, looks down -z, turns depth on and is placed with `lookAt` or `setView`; `screenToWorld(sx, sy, 0)` and `(…, 1)` give a pick ray. `renderer.camera` is `Camera.ortho2d(logicalWidth, logicalHeight)` by default and can be reassigned. Each frame the renderer writes the camera block (`EngineCamera` at `@group(0) @binding(1)`: `view`, `proj`, `view_proj`, `camera_pos`, `viewport` in scene target px, `view_index` = 0) beside the globals (`@binding(0)`: `logicalSize`, `targetSize`, `time`, `dt`) in one upload, and `engine_vertex` projects with `camera.view_proj`. The renderer reads `layers` (draws with `layers & camera.layers === 0` are skipped), `depthTest` (off: no depth attachment, draws sorted by `order` then submission), `depthWrite` (both flags off for `ortho2d`, on for `perspective`) and `viewProjection` (clip-space depth is the depth sort key, so the sort agrees with the depth buffer for every projection) from the camera passed to `render(frame, camera, target)` (ws/render-call); the clip line is `camera.view_proj * vec4(world.xyz, 1)`, so the instance's world z reaches the depth buffer. The layout's `freeRect` (CSS px) feeds `fitRect` once converted to screen units (`surface.clientToLogical` on its corners). *Planned:* `view_index` 1 and per-eye cameras arrive with XR.

**Transforms, layers and instances.** Every draw is one 28-float instance whose placement is a 3×4 world matrix, so 2D sprites, meshes and later voxels share one vertex path. *Today:* `render/transform.ts` exports `Transform` (position xyz, rotation about Z for 2D as `rotation` in radians, or any 3D rotation as a unit quaternion via `setQuaternion` / `setAxisAngle`; scale xyz; optional `parent`) with a cached 3×4 row-major `world` matrix that recomputes only when it or an ancestor changes. `frame.sprite(mat, DrawParams)` still works and writes the matrix directly (`writeMatrix2d`, exact at rotation 0, no allocation); `frame.sprite(mat, transform, params?)` and `frame.mesh(mesh, mat, transform, params?)` take a `Transform`. Every draw carries `layers` (u32, default 1) and `order` (sort key, default 0). Without depth, draws sort by `order` then submission index, so the default reproduces submission order and batching exactly. With `camera.depthTest`, keys are `order`, then opaque before blended, then view-space depth (opaque front-to-back, blended back-to-front), then submission index; the depth24plus attachment is allocated only then. Meshes carry a `VertexLayout`: `VERTEX_LAYOUT_2D` (8 floats, unchanged; `quadGeometry()` unchanged) or `VERTEX_LAYOUT_3D` (xyz, normal xyz, uv, rgba = 12 floats). Materials build pipelines lazily per (vertex layout, depth mode) from a per-layout prelude (`materialPrelude(layout)`), so a game's `fs_main` is unchanged. Drawables declare depth themselves: `ParticleSystem.draw(pass, frame)` picks a pipeline with `depthStencil { format: frame.depthFormat, depthWriteEnabled: false, depthCompare: 'less-equal' }` (one per format, built lazily) when the frame has depth. *Planned:* instance `flags` (float 25) are reserved.

**Renderer.** The renderer records draws into a `Frame` and draws them for one camera into one target; it owns no camera and no frame of its own beyond conveniences. *Today:* `renderer.beginFrame(time, dt)` returns the reusable `Frame`; `renderer.render(frame, camera, target = renderer.target)` encodes one scene pass of the recorded draws for that camera into a `SceneTarget` (colour + emissive, `SCENE_FORMAT`, plus a `depth24plus` attachment made on first use by a depth camera); `renderer.endFrame()` runs post (or present) from `renderer.target` and submits, and calls `render(frame, renderer.camera)` itself when nothing rendered in between, so `createGame`'s single-camera path is unchanged. Several `render` calls per frame (split screen through `camera.screen`, which sets the viewport and scissor as a fraction of the target when it lies inside the unit square, else in logical px; UI over world through layers; an offscreen view through `renderer.createSceneTarget(desc)`) share one instance buffer at increasing offsets and one 512-byte uniform buffer plus bind group per view (`engine-globals`, `engine-globals-1`, …; pooled, so steady state allocates nothing); the first view into a target clears it (colour from `frame.clearColor`, depth to 1), later views load. `renderer.stats` is reset in `beginFrame` and summed over the views. `Renderer.render` outside `beginFrame`/`endFrame` throws. *Planned:* a `SceneTarget` per eye for XR.

**Frame loop.** `GameLoop` as today (fixed 60 Hz update, variable render), but `render(camera, target, alpha)` takes the camera and the target as inputs instead of reading them from the renderer. The host decides who schedules frames (rAF, Electron, later `XRSession.requestAnimationFrame`). *Today:* `GameLoop` and `FixedStepper` in `core/loop.ts` (fixed step, `maxFps` cap, pause) call `render(alpha, time)` from the frames of a `FrameSource` (`GameLoopOptions.frames`: `createGame` passes its `Host`; the default is `defaultHost()`, read on the first `start()`; tests pass a stub they step by hand). The loop never calls `requestAnimationFrame` itself. The game's render callback records a `Frame` and calls `renderer.render(frame, camera, target?)` per camera (or lets `endFrame` render `renderer.camera`). With `GameLoopOptions.fixed: false` (what `createGame({ sim: false })` uses) there is no accumulator: `update(dt, time)` runs once per rendered frame with the real clamped delta, `render` gets `alpha` 1, and pause still skips update. `Scene<Ctx, Frame>` and `SceneStack` in `core/scene.ts`. *Planned:* `Scene.render(frame, camera, alpha)` once scenes take the camera from the game instead of `renderer.camera`.

**Host.** `interface Host extends FrameSource { kind; requestFrame; cancelFrame; openExternal; copyText; fullscreen; storage; window?; embed }`. Implementations: `web` (detects iframe vs top and wraps today's D-036 link service) and `electron` (preload bridge). After Phase 1 the engine never calls `window.open`, `navigator.clipboard` or `localStorage` directly. *Today:* `host/` (`@thunderclap/engine/host`) has the `Host` type, `createWebHost({ win? })` and `defaultHost()` / `setDefaultHost()`. The web host also exposes `clipboardWriteAllowed()`; `fullscreen` is `{ available, active, toggle, watch }` and `storage` is `{ kind, open(): StorageLike | null }`. `save` (`createSaveStore`, `listSlots`), `persistMixer` and the `externalLink` widget take `host` and default to `defaultHost()`. `window.open`, `navigator.clipboard`, `execCommand` and `localStorage` appear only in `host/web.ts` and `host/web-links.ts`; the fullscreen DOM calls stay in `platform/device.ts`, which the web host wraps. The Electron host lives in this repo as `packages/host-electron` and provides `createElectronHost()` (`@thunderclap/host-electron`): the same interface over the preload bridge `window.thunderclap`, `kind: 'electron'`, storage the renderer's `localStorage` (served from the fixed origin `app://bundle`), and `window` with `close`, `minimize`, `toggleMaximize` and `setTitle`. A game installs it with `setDefaultHost` or passes it to its ctx; the engine never imports it. Frames come from the host (ws/render-call, D-044): `FrameSource { requestFrame(cb: (timeMs) => void): number; cancelFrame(handle) }`, wrapped over the window's `requestAnimationFrame` on web and Electron; `GameLoop` schedules through it, so an XR session is a `Host` implementation (`XRSession.requestAnimationFrame`), not a redesign. *Planned:* that XR host.

**Input.** The action map for keyboard, mouse, touch, pen and gamepad, with `blocked()`, `lastDevice`, queued taps, iframe-safe `preventDefault`, injectable pads and public feed methods for tests; `ui/padnav.ts` drives modal panels from the pad and `ui/menu-nav.ts` (`menuNav`) drives non-modal menus. `Gestures` (`input/gestures.ts`) recognises tap, double tap, long-press (450 ms), pan, drag (with its origin) and pinch (scale) from pointer events, with thresholds in CSS px (pan 10) and positions in game space through the same `PointerTransform`. It reports per tick like `Input`: one discrete gesture per kind per tick (extras queue), continuous ones every tick from `start` to `end` or `cancel`. `input.setGestures(g)` links it: the gestures share `blocked()` and the transform, attach with `Input.attach`, advance in `Input.update()`, and can be bound as actions (`{ gesture: 'tap' | 'doubleTap' | 'longPress' | 'pan' | 'drag' | 'pinch' }`), so a game can map tap to `select` and long-press to `info` without reading gestures. While blocked nothing is reported and a running pan, drag or pinch gets one `cancel`. The `magnify` option (`input/magnify.ts`, ws/port-altar) is loupe and snap for small touch targets: while one touch pointer is down each tick reports `gestures.aim`, the finger raised by `lift` (56 CSS px) while it drags, snapped by the game's `snap(x, y)` (usually `snapToGrid`, the nearest accepted cell within half a pitch), and while `pitch()` is below `below` (44 CSS px) a `Loupe` beside the finger magnifies the aim point `zoom` (2.5) times with the target ringed. The aim the finger lifted at is reported once more (`ended`) on the drag's `end` tick, so a dragged thing lands where it was aimed. Mouse and pen never aim. The loupe and its leader line (dense-board-4) are `position: fixed` elements in client px outside the overlay's layers, so overlay units never apply to them. *Today (ws/input-rays):* every pointer is a ray. `createPointerRouter({ camera, testers, sources })` (`input/pointer-router.ts`) turns each pointing source into a `Ray { origin, dir }` through the active camera (`screenRay`: `camera.screenToWorld` at depth 0 and 1, or 0.5 when the far plane is infinite; no allocation per frame) and keeps, per pointer, the nearest `Hit` over the game's `HitTester`s (`(ray) => Hit | null`; shipped: `planeTester(z)` and `aabbTester(boxes)`, which also covers flat 2D quads). It emits `hit`, `hitEnd`, `select` and `secondary` (core `Emitter`). Sources implement `PointerSource { poll(camera) => PointerSample[]; attach?; detach? }`: `ScreenPointers` (mouse and pen hover; a touch is a pointer while down plus one tail tick, and a single touch aims through the magnify `aim`) is built in, and `PadCursor` is a stick-driven cursor clamped to `camera.screen`. `input.setPointers(router)` links it like gestures (shared `blocked()`, transform, attach, polled in `Input.update()`), and adds the binding kinds `{ pointer: 'select' | 'secondary' }` and `{ xr: 'trigger' | 'squeeze' | 'pinch', hand? }`. When the input binds the router's `selectAction` (default `select`), a press of that action from any binding selects the primary pointer's hit; otherwise each pointer's button edge does. While blocked every hit ends and nothing selects. *Planned:* an XR source (ws/xr) implementing `PointerSource` from `XRInputSource.targetRaySpace` per hand, with `select = trigger || pinch`, `secondary = squeeze`, pinch distances in metres and `x`, `y` NaN; nothing in the router changes. `createGame` building the router and exposing `ctx.pointers`.

**Layout.** One overlay, laid out in CSS px on every form factor (ws/one-overlay, D-044). A `LayoutSpec` names regions (`top`, `left`, `right`, `bottom`, `cardLane`, `captionLane`, `modal`) per form factor (`phone`, `tablet`, `desktop`, each in `landscape` or `portrait`), with safe areas. Games register widgets against regions and the engine places them with CSS grid. The layout reports the free rect, so the world can frame into what the UI leaves. Density tokens `--tc-text-min`, `--tc-tap-min` and `--tc-text-scale` replace the game's `--lr-*` variables. *Today:* `createOverlay` in `ui/overlay.ts` builds one `.tc-overlay` root over the whole parent (letterbox bars included), with no transform, and its layout (`overlay.layout`; `ctx.ui.layout` in a game). Layers, bottom to top: `hud` and `captions` sit on the **frame** (the canvas rect, `--tc-frame-x/y/w/h`, set by `setFrame` on every resize) and clip to it; `layout` covers the whole root; `panels` and `toasts` sit on the frame in `frame` units and cover the root in `css` units. Each form's `FormSpec.units` picks the units (`data-units` on the root, `overlay.units`): `frame` (desktop, tablet) sizes the base UI in design px of the 1920×1080 frame, `--tc-dpx` CSS px each, so it keeps its proportions to the canvas; `css` (phones) takes `cssPxTheme` sizes as CSS px. `--tc-unit` is what one px of a design-px stylesheet draws as on each layer: `--tc-dpx` on the frame's layers, 1px in the regions and, in `css` units, in panels and toasts. `toFrameUnits(css)` (in `ui/text-scale.ts`) rewrites a design-px sheet's `Npx` to `calc(N * var(--tc-unit, 1px))`; games pass their sheets through it and `scaleFontSizes`. World-anchored DOM (labels over 3D objects) goes in `hud` at its design coordinates times `--tc-unit` (the same point as `surface.logicalToClient`), so it follows every resize without JS. Native controls whose parts are CSS px (range thumbs, select arrows) are zoomed by `--tc-zoom` (the scale as a number) on the frame's layers. `createLayout(overlay, spec?)` in `ui/layout.ts` classifies the form factor (`phone-landscape`, `phone-portrait`, `tablet`, `desktop`: a phone is a coarse pointer with a short side of at most 600, or any view under 480), resolves each form's px tracks and grid areas inside the safe area (`env(safe-area-inset-*)`, overridable with `--tc-safe-*` or `setSafeArea`), collapses tracks whose regions have no widgets, and draws the same px grid in the DOM. `layout.add(el, { place: { default, <formFactor> } })` moves a widget between regions on an orientation change; `'hidden'` hides it; `{ region: 'free', rect, reason }` is the escape hatch (logged once with `console.info` and listed in `freeUses`); `WidgetHandle.remove()` puts an element back where it was before `add`. `layout.freeRect` is the `fill` region, the space the world gets; `onChange` reports every re-layout. `layout.setForms(forms | null)` lays a scene's own tracks over the spec's, per form factor and field by field, for regions that follow the scene's content; the scene sets it on enter and on resizes and clears it on exit. `layout.dockCaption()` moves the caption card into `captionLane` (`caption.dock(host)`); undocked, the card sits in a frame corner and a game steers it with `caption.onPlace` and `caption.relayout()`. The layout owns `--tc-tap-min` (44 on touch forms), `--tc-text-min`, `--tc-region-pad`, `--tc-safe-*-px` and `--tc-modal-*`; buttons, toggles, sliders and panels honour them. `--tc-text-scale` and `scaleFontSizes` are in `ui/text-scale.ts`; `platform/device-mode.ts` (`data-phone`, `data-touch`) and `ui/rotate-card.ts` are interim API; the phone stylesheets stay in the game (`ui/phone-base.ts` and each scene's `*-phone-styles.ts`). *Planned:* ws/camera (D-044) feeds `freeRect` to `Camera.fitRect` and deletes `device`, `setFill` and the fill bands.

**Two overlays (history, ws/port-chrome).** Between ws/port-chrome and ws/one-overlay the engine ran two overlays: `ctx.ui`, the legacy 1920×1080 overlay shrunk by one CSS `scale()`, and `ctx.chrome` (`createCssChrome`), a CSS-px overlay with the layout on it, into which the legacy `panels` and `toasts` layers moved while a phone form factor was active (`cssForms`). It let a game port its scenes one form factor at a time. ws/one-overlay (D-044) deleted it: `createCssChrome`, `CssChrome`, `CssChromeOptions`, `PHONE_FORMS`, `EngineCtx.chrome`, `CreateGameOptions.overlay`, `createOverlay({ legacyScale })`, `overlay.setRect`/`onRect` and `caption.avoid()` are gone, and panels and toasts never move between roots. See CHANGELOG.md, "Removed (ws/one-overlay)".

**UI, Audio, Save, FX, Post.** The APIs are unchanged; the overlay's scaling model is the one change inside UI. *Today:* `ui/` (overlay stack, panels, widgets, toasts, captions, loupe, external-link widget, theme tokens), `audio/` (WebAudio buses, synth, recipes, mixer persistence), `save/` (versioned slots, migrations, quota- and blocked-storage-safe), `fx/` (GPU particles, flicker) and `post/` (bloom, god rays, fog, vignette, grade, quality tiers). Each module has a README with usage. `save` takes its storage from the host (`host.storage`).

**Analytics.** Typed, batched game events handed to a sink the game supplies; the engine makes no network call (VISION rule 4). *Today:* `createAnalytics<E>({ sink, session?, clock?, context?, onError?, maxBatch? })` in `analytics/` returns `emit(name, props)`, `flush()` and `attach(ctx)`. Each event carries `name`, `props`, a per-page-load `session`, a monotonic `seq` and `t`. `attach` emits `game_start` (form factor, host kind, DPR, viewport, embed, build), wraps `ctx.hooks.hide`, `show` and `deviceLost` (the game's hooks still run), emits `device_lost`, and on `hooks.hide(reason)` (hidden, pagehide, freeze) or device loss emits `session_end` with that reason and flushes; `show` re-arms it. It adds no lifecycle listeners of its own. A failing sink goes to `onError`; `emit` and `flush` never throw. *Planned:* a template-provided `sendBeacon` sink in the game template, and `level_start` / `level_complete` conventions.

**Scene and Ctx.** `Scene<Ctx, Frame>` and `SceneStack` are in `core/`. *Today:* `createGame(opts)` in `core/game.ts` (exported from the root entry `@thunderclap/engine`, not `./core`, because it is the top layer and pulls in every module) builds the engine's ctx and resolves to `EngineCtx`, or to `null` when WebGPU is missing (the unsupported screen is shown). It blocks browser zoom (double-tap, pinch, ctrl+wheel; option `blockBrowserZoom`, default on), boots the letterboxed surface, and builds the renderer, post stack, particles, host, save (`opts.save(host)`, opt-in), overlay, pad nav, audio (with `persistMixer` when `mixerKey` is set), input (blocked under a modal) and its pointer router (`createPointerRouter({ camera: () => renderer.camera })`, linked with `input.setPointers`). It wires resize (renderer, the overlay's frame via `ui.setFrame`, which re-lays the layout), the loop (frames from `host`; input → pad nav → `hooks.update` → particles → scenes, in fixed steps of `sim.step`, default 1/60; `hooks.beforeRender` → scenes → `hooks.afterRender`), page lifecycle (hidden, pagehide, freeze: stop the loop, `hooks.hide(reason)` with `HideReason` `'hidden' | 'pagehide' | 'freeze'`, flush the save; shown: resume the loop, then `hooks.show(reason)`, unless the device was lost) and device loss (halt the loop for good, `hooks.deviceLost`, halt audio, flush, reload screen). Two parts are opt-in so a pure client of a server-authoritative game (VISION pillar 6) boots through the same call: **save**: without `opts.save`, `S` is `null`, `ctx.save` is `null` (typed `null`; such a ctx is not assignable to `EngineCtx<A>`, whose default `S` is `FlushableSave`, and `createGame` does not infer `S` from a return annotation), hide and device loss flush nothing, and nothing reads `host.storage` (leave `mixerKey` out too); **sim**: `opts.sim: false` runs the loop at render rate (`GameLoopOptions.fixed: false`), so input → pad nav → `hooks.frame(dt)` → particles → scenes' `update(dt)` run once per rendered frame with the real delta and `hooks.update` never runs. Callers that pass `save` and no `sim` get exactly the old behaviour. The harness's `game.html?mode=client` boots that way (e2e/client.spec.ts). `EngineCtx<Action, Save, Ctx>` (`Save extends FlushableSave | null`) holds `design`, `surface`, `gpu`, `renderer`, `post`, `particles`, `input`, `padNav`, `audio`, `ui` (the one overlay, with its layout as `ui.layout`; `CreateGameOptions.layout` is its `LayoutSpec`), `host`, `pointers` (`PointerRouter<unknown>`), `save`, `stack`, `loop`, `hooks` and `onDeviceLost(fn)`. A game widens that same object with its nouns (`Object.assign(engine, {...})`), so scenes get one ctx; Last Rune's `GameCtx extends EngineCtx` in `games/last-rune/game/ctx.ts` (in the game repo, not here). `device`, `setFill(key)` and `CreateGameOptions.fillBands` are gone (ws/render-call, D-044): a 2D game frames `ui.layout.freeRect` with `renderer.camera.fitRect`. *Planned:* `camera` and `gestures` join `EngineCtx`; the layout stays on `ui`. The fixed pipeline (post, particles, audio, pad nav, loop order) opens up in a later step.
