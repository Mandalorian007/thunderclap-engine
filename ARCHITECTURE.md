# ThunderClap engine: architecture and contracts

`@thunderclap-engine/engine` is the WebGPU engine The Last Rune is built on. It knows nothing about any game. This file is the target the PM reviews promotions and public API changes against (D-041, [refactor plan](https://github.com/Mandalorian007/last-rune/blob/main/docs/engine/refactor-plan.md)). Decision numbers (D-0xx) and `docs/` paths in this repo refer to [The Last Rune](https://github.com/Mandalorian007/last-rune), where the engine was built. Each contract says what exists **today** (1.0.0 plus the unreleased work in CHANGELOG.md) and what is **planned**, with the workstream that delivers it.

## Package shape

```
thunderclap-engine/
  package.json        # @thunderclap-engine/engine; the "exports" map is the public API
  pnpm-workspace.yaml # packages: ['packages/*']; the engine stays the root package
  packages/           # the three hosts, each published to npm on its own 0.x line; each depends on
                      # the engine via "workspace:*" (links the root) and peers on ^1.0.0 when packed
    host-electron/    # @thunderclap-engine/host-electron: the Electron shell (main, preload),
                      # createElectronHost() and the `thunderclap-desktop` dev/package command
    host-capacitor/   # @thunderclap-engine/host-capacitor: createCapacitorHost() for iOS and Android
    host-pwa/         # @thunderclap-engine/host-pwa: createPwaHost() and the pwaPlugin Vite plugin
  src/
    index.ts          # the "." entry: createGame and its types
    analytics/  anim/  assets/  audio/  core/  fx/  geom/  host/  i18n/  input/  kit/  nav/  net/  platform/  post/  render/  save/  ui/
  harness/            # noun-free e2e pages: index.html boots the platform layer (window.__harness);
                      # game.html boots through createGame (window.__harnessGame); rays.html, mesh.html,
                      # views.html, stream.html, weather.html, look.html, anchors.html, gltf.html and
                      # xr.html use cameras; ui.html, layout.html and gestures.html are DOM only
  e2e/                # engine e2e specs, fixtures, ports, itch-style iframe wrapper
  templates/          # copyable games (puzzle, first-person); `pnpm create-game <dir> --template <name>`
                      # (scripts/create-game.mjs) copies one out as a standalone project on the engine
  scripts/            # tooling, no runtime: build.mjs (`pnpm build`) writes dist/ for npm; pack-smoke.mjs
                      # (`pnpm check:pack`) installs the packed tarballs into a fresh consumer; bake.mjs
                      # (`pnpm bake <config>`) runs the nav and collider bakes and writes a manifest
  dist/               # `pnpm build` output (gitignored): ESM JavaScript and .d.ts, what npm ships
  playwright.config.ts  # the viewport/device/wrapper matrix every engine spec runs on
  ARCHITECTURE.md     # this file
  CHANGELOG.md
```

**Test ownership (D-041 addendum 2).** The engine verifies platform capability once, for every game: unit tests (`src/**/*.test.ts`, Vitest) and e2e specs (`e2e/`, Playwright) run against the `harness/` page. Every spec runs on the whole matrix in `playwright.config.ts`: desktop 1280×720 and 1920×1080, iPad 1180×820, four phones (667×320, 844×340, 932×380, 915×360, touch at DPR 2), and the harness inside an itch-style cross-origin iframe. Two upright rows, `phone-port` 390×844 and `tablet-port` 820×1180, run the layout spec only. A new platform capability (host, gestures, layout, lifecycle) adds a probe to the harness and a spec here, not in a game. Games test product only. `pnpm bench` runs the scene ladder in `harness/bench.html` and rewrites `docs/BENCH.md` (ws/bench). *Today:* frame cost is also counted, not only timed (ws/budget, E-041): `createWorkMeter` in `@thunderclap-engine/engine/testing` wraps the fake device in a Proxy and reports per frame the GPU calls by kind, the typed arrays allocated, the clock reads and a per-view split, and `budget()` and `expectProportional()` hold them in any unit test. `src/render/baseline.budget.test.ts` pins the 1.3 numbers for every bench rung and the 2D harness scenes (with call-trace goldens) in `src/render/baseline.budget.json` and the "Counted work" section of `docs/BENCH.md`, which `pnpm bench` keeps.

Games import only the exports map: `@thunderclap-engine/engine` (the `"."` entry: `createGame` and its types) and `@thunderclap-engine/engine/<module>` for `analytics`, `anim`, `assets`, `audio`, `core`, `fx`, `geom`, `host`, `i18n`, `input`, `nav`, `net`, `platform`, `post`, `render`, `save`, `tween`, `ui` and `voxel`, plus `@thunderclap-engine/engine/testing` (`src/testing/index.ts`: the fake GPU, a fake host, a fixed clock and `createTestGame`, for unit tests only). Each subpath is that module's `index.ts`; anything not re-exported there is internal. `pnpm check:boundaries` (`scripts/check-boundaries.mjs`, part of `pnpm check`) fails if anything under `src/` imports from outside `src/` or through the package name, or if `harness/`, `e2e/`, `examples/` or `templates/` imports a subpath outside the map or reaches into `src/` by a relative path. Inside the package, modules import each other by relative path. `voxel` (block grids, a Worker-ready greedy mesher with its bridge, a chunk renderer over `render`'s `Mesh`, block picking and the `VOXEL_WGSL` prelude) is noun-free like the rest: block ids, their texture layers and what a click does stay in the game. A game, in its own repo, is held to the same map by its own checks.

**Workspace.** The engine is the root package, so a dependency on this repo by URL still resolves to it. `packages/host-electron`, `host-capacitor` and `host-pwa` are workspace packages that depend on the engine with `"workspace:*"`, which pnpm links to the root. Each is self-contained: the root `tsconfig.json` does not include `packages/`, and `pnpm check` runs `check:host-electron`, `check:host-capacitor` and `check:host-pwa` (typecheck, lint, unit tests) after the engine's own checks. Desktop builds of the harness shell go to `dist/desktop/` at the repo root (gitignored). The engine never imports a host.

In the workspace every `exports` entry points at `./src/*.ts`, so the harness, templates and tests run on source. What npm ships is a build: `pnpm build` compiles the engine and each host with `tsc` to `dist/` (plain ESM JavaScript and `.d.ts`, runnable without a bundler), and host-electron's shell to `out/`. Each manifest's `publishConfig` points `exports` at `dist/`, and `pnpm pack` swaps it in. `@thunderclap-engine/engine` (1.1.0) and the three hosts (0.1.0) are on the public npm registry; a `v*` tag publishes from CI ([Releasing](docs/releasing.md), E-037), and `pnpm check:pack` proves the packed tarballs install, typecheck and build in a fresh project. host-electron also ships a `thunderclap-desktop` bin, so a game gets its desktop dev loop and installers from the package alone (#2). A game starts in its own repo with `pnpm create-game <dir> --template <name>` (ws/scaffold): the template is copied out of `templates/`, its `package.json` renamed and pointed at the engine (`--engine <spec>` for any spec, or a directory for a `link:` to a clone; without it, `^<version>` from npm, since `PUBLISHED` in `scripts/create-game.mjs` is `true`), and its `CLAUDE.md` kept. Every template has `build` (`vite build` to a static `dist/`) and `preview` scripts; `pnpm check` scaffolds each one, installs it offline, typechecks and builds it (`check:create-game`).

**API surface (ws/harden-api).** *Today:* `api/<entry>.api.txt` is the committed snapshot of the public surface, one file per `package.json` `exports` entry that points into `src/` (`api/index.api.txt` for `"."`, `api/testing.api.txt` for `./testing`). `scripts/api-surface.mjs` writes it from the repo's own `tsc` declaration emit (tests excluded): every exported name, sorted, each with its declared signature, tagged `alias of` or `type-only` where that applies, with comments, private members and inline `import("…")` qualifiers stripped and `@deprecated` kept, so a doc edit or a file move is not an API change but a deprecation is. `pnpm check:api` (inside `pnpm check`) fails on any difference from the committed files and prints the diff; `pnpm api:update` rewrites them (and deletes a file whose entry is gone). A branch that changes the public API commits the updated `api/*.api.txt`, so every surface change shows up in review as a diff of that file. Since `engine-v1.0.0` (ws/v1-cut) the snapshots are the frozen surface (each opens with an `engine-v1.0.0 frozen surface` header line) and `check:api` also fails when an `api/` file differs from the last release (the tag `v<version>`, else the commit that set the version) unless CHANGELOG.md `## Unreleased` has a *Breaking* or *Added* entry naming its module (`scripts/api-changelog.mjs`, tested in `scripts/api-surface.test.mjs`); `pnpm release` dates that section and opens a fresh one. The engine itself declares nothing `@deprecated`; `check:deprecated` guards the next deprecation with no exemption markers.

## Ground rules

1. **Promotion rule.** Code enters the engine only if Last Rune uses it, the next game plausibly would, and its API has zero game nouns.
2. **Dependency direction.** `games/*` imports `@thunderclap-engine/engine`; the engine never imports a game. A game's `rules/` imports nothing from the engine or the DOM.
3. **No runtime dependencies** without a DECISIONS entry (D-008). WebGPU is the only renderer.
4. **Seams, not features.** 3D and XR arrive capability by capability with the game that needs them (VISION rule 6). The engine grew the seams first (`Surface`, `Camera`, the frame loop, `Host`, `PointerSource`) and then XR through them (ws/xr, E-013): XR is *Today* behind `createGame({ xr })` (`XrSurface`, `createXrHost`, `XrPointerSource`, `ctx.xr.enter()/exit()`), with no redesign of the 2D path, which stays pixel-identical. The WebXR types are the engine's own module exports (`platform/xr-types`), never globals, each a structural subset of `@types/webxr`'s, so a game may install `@types/webxr` beside the engine and pass its sessions and frames in (E-039; `pnpm check:pack` proves it with `skipLibCheck` off). The post stack runs per eye through `renderer.resolve` (ws/xr-post). Nothing XR-specific waits for Gate 5; what comes after Gate 5 is whatever the next game names.

## Contracts

**Surface.** Owns the canvas, the swapchain, DPR, the backbuffer size and the letterbox fit. It exposes `rect` (CSS px), `backbuffer` (device px), `clientToLogical` and `onResize`. *Today:* `Surface` is an interface (ws/platform-surface; a game-made or no-DOM surface implements it with no cast), and the value `Surface` / `mountSurface` in `platform/surface.ts` is the DOM canvas that implements it; it exposes `rect`, `fitRect`, `backbuffer` (device px), `clientToLogical`, `logicalToClient`, `containsLogical`, `onResize` and `setFrame(rect | null)` (letterbox inside a part of the container, CSS px, e.g. the layout's `freeRect`), over the pure letterbox math in `platform/letterbox.ts` (`computeLetterbox`, `computeBackbuffer`, `clientToLogical`, `logicalToClient`); `SurfaceOptions.fit` (ws/surface-fill, #1) is `'contain'` (default, unchanged) or a cover fit (`'cover'` or `CoverOptions`: `minVisibleHeight`/`minVisibleWidth` band, `focusX`/`focusY`, `belowScale`) where the canvas covers the container or the frame (then not clamped to the container) and the design is cropped to the band (`computeCover`), `setFit(fit)` switches it at runtime and `visibleRect` is the design rect on screen (`visibleLogicalRect`; both optional on the interface, always on the DOM surface); the coordinate maps, the resize listeners (so the overlay frame) and `Camera.fitFreeRect` all read the covered `rect`; `initGpu` configures the swapchain. The fill-width fit (`setFill`, `computeFillWidth`, `FillWidthOptions`) is gone (ws/plumbing, E-010): a 2D game frames `ui.layout.freeRect` with `Camera.fitFreeRect(worldRect, freeRect, surface)` (D-044). The renderer draws into a `SceneTarget` through `renderer.render(frame, camera, target)` (ws/render-call). `XrSurface` in `platform/xr-surface.ts` (ws/xr) is the per-eye counterpart, a separate class rather than a `Surface` (no `rect`, `backbuffer` or `onResize`; the headset owns those): an `XRGPUBinding` projection layer in `SCENE_FORMAT` + `depth24plus`, and per frame `views(frame): XrEyeView[]`, each with a depth-on `Camera` (`viewIndex` 0/1, the view's projection and inverse pose, `screen` the viewport fraction) and a `SceneTarget.external(...)` over the layer's `getViewSubImage` colour and depth textures (one shared target when the eyes are side by side on one texture, so the first eye clears and the second loads). With `scene: true` (ws/xr-post, what `createGame` passes) the surface also keeps `scene`, one eye-sized HDR `SceneTarget` (allocated on the first posed frame, resized on eye-size change), the eye cameras cover it whole, the layer is made in the post stack's output format (`renderer.format`) without depth, and each eye is rendered into `scene` and resolved into its `viewport` of the layer. The eye cameras cull (`cull: true`), and `head`, the camera post and world UI see, has a projection covering both eyes' frustums (their union, pulled back behind the eyes inside the projection so `head`'s pose stays the viewer's); the layer's textures are wrapped once per texture, so a compositor that cycles them allocates nothing per frame (ws/xr-fixes).

**Camera.** A view-projection matrix plus `worldToScreen` and `screenToWorld` (the inverse projection; touch aiming uses it). Presets: `ortho2d(designW, designH)`, where 1 unit = 1 design px, and `fitRect(rect, viewport)`, which fits a world rect into a viewport. Depth test and depth write are camera-preset flags; the 2D preset leaves both off. *Today:* `Camera` in `render/camera.ts` (ws/camera) holds `view`, `projection` and `viewProjection` (column-major `Float32Array(16)` from `mat4` in `core/math.ts`, `@thunderclap-engine/engine/core`; cached, recomputed on read after a change), `position`, `depthTest`, `depthWrite`, a `layers` membership mask (u32, default all bits; the draw sort `order` belongs to ws/transforms) and `screen`, the rect clip space spans in the units `worldToScreen` returns and `screenToWorld` takes. `Camera.ortho2d(w, h)` is origin top-left, y down, and looks down +z (right-handed with y down: larger z is farther), spanning world z in ±`ORTHO2D_HALF_DEPTH` (1024; z = 0 sits at clip depth 0.5), with `screen` = the design space; its 2D controls `x`, `y`, `zoom` and `rotation` are the earlier 2D camera's, and its `viewProjection` uses the same arithmetic, so the 2D path is pixel-identical. `fitRect(rect, viewport = screen)` sets those controls (rotation 0) so a world rect is contained and centred in a viewport given in screen units. `Camera.perspective(fovY, aspect, near, far)` is right-handed, looks down -z, turns depth on and is placed with `lookAt` or `setView`; `screenToWorld(sx, sy, 0)` and `(…, 1)` give a pick ray. `setPerspective(fovY, aspect, near, far)` on any camera sets the same depth and cull flags (`setProjection` stays raw), and the per-frame helpers `viewZ`, `invViewProj`, `projectMany` and `frustumCorners` (ws/camera-ergo) project many points or read the frustum without allocating. `renderer.camera` is `Camera.ortho2d(logicalWidth, logicalHeight)` by default and can be reassigned. Each frame the renderer writes the camera block (`EngineCamera` at `@group(0) @binding(1)`: `view`, `proj`, `view_proj`, `camera_pos`, `viewport` in scene target px, `view_index` = `camera.viewIndex`, default 0) beside the globals (`@binding(0)`: `logicalSize`, `targetSize`, `time`, `dt`) in one upload, and `engine_vertex` projects with `camera.view_proj`. The renderer reads `layers` (draws with `layers & camera.layers === 0` are skipped), `depthTest` (off: no depth attachment, draws sorted by `order` then submission), `depthWrite` (both flags off for `ortho2d`, on for `perspective`) and `viewProjection` (clip-space depth is the depth sort key, so the sort agrees with the depth buffer for every projection) from the camera passed to `render(frame, camera, target)` (ws/render-call); the clip line is `camera.view_proj * vec4(world.xyz, 1)`, so the instance's world z reaches the depth buffer. `fitFreeRect(rect, freeRect, surface)` takes the layout's `freeRect` in CSS px, maps it onto `screen` through `surface.rect` and fits the world rect into it, allocating nothing (ws/plumbing). Per-eye cameras (ws/xr): `setViewMatrix(m)` (an alias of `setView` for an `XRView`'s `transform.inverse.matrix`) and `setProjection` take the headset's matrices; `XrSurface` keeps one `Camera` per eye with `viewIndex` = eye and `depthTest` on.

**Transforms, layers and instances.** Every draw is one 28-float instance whose placement is a 3×4 world matrix, so 2D sprites, meshes and later voxels share one vertex path. *Today:* `render/transform.ts` exports `Transform` (position xyz, rotation about Z for 2D as `rotation` in radians, or any 3D rotation as a unit quaternion via `setQuaternion` / `setAxisAngle`; scale xyz; optional `parent`) with a cached 3×4 row-major `world` matrix that recomputes only when it or an ancestor changes. `frame.sprite(mat, DrawParams)` still works and writes the matrix directly (`writeMatrix2d`, exact at rotation 0, no allocation); `frame.sprite(mat, transform, params?)` and `frame.mesh(mesh, mat, transform, params?)` take a `Transform`. Every draw carries `layers` (u32, default 1) and `order` (sort key, default 0). Without depth, draws sort by `order` then submission index, so the default reproduces submission order and batching exactly. With `camera.depthTest`, keys are `order`, then opaque before blended, then clip-space depth from the render camera (opaque front-to-back, blended back-to-front), then submission index; the depth24plus attachment is allocated only then. Meshes carry a `VertexLayout`: `VERTEX_LAYOUT_2D` (8 floats, unchanged; `quadGeometry()` unchanged) or `VERTEX_LAYOUT_3D` (xyz, normal xyz, uv, rgba = 12 floats). Materials build pipelines lazily per (vertex layout, depth mode) from a per-layout prelude (`materialPrelude(layout)`), so a game's `fs_main` is unchanged. A `Mesh` has a `capacity` (vertices, indices; `createMesh` takes initial data, a capacity or both) and `update({ vertices?, indices?, vertexCount?, indexCount? })`, which writes each view in place from its own `ArrayBuffer` (a buffer transferred from a Worker is uploaded without a main-thread copy), reuses the GPU buffers while the counts fit, grows them 1.5× only when they do not (`growths` counts it) and lets `indexCount` shrink the draw without reallocating, and also takes a Worker's reply as-is (`MeshReply { buffer, vertexCount, indexCount?, indexOffset?, bounds? }`, ws/ergo-3d); `harness/stream.html` streams chunk meshes from a Worker this way. An indexed mesh with `indexCount` 0 draws nothing. `VERTEX_LAYOUT_SKINNED` (ws/skinning: the 3D layout plus `uint8x4` joints and `unorm8x4` weights, 56 bytes) skins on the GPU: the material binds a `SkinPalette` (a storage buffer of 3×4 joint matrices, 12 floats each, `instances × joints`, the layout `anim`'s `skinMatrices` writes; `BindingDesc.buffers` at `@group(1) @binding(16)`), the draw names its slot in `params.w`, and `materialPrelude` emits `WGSL_SKIN` (`engine_skin`) only for that layout so `engine_vertex`, the shadow pass's `vs_main` and the 2D/3D preludes are unchanged; the shadow pass binds the material group as group 1 for a skinned caster, so its shadow follows the pose. Drawables declare depth themselves: `ParticleSystem.draw(pass, frame)` picks a pipeline with `depthStencil { format: frame.depthFormat, depthWriteEnabled: false, depthCompare: 'less-equal' }` (one per format, built lazily) when the frame has depth. Each mesh draw also carries `mesh.bounds` (a bounding sphere: given with the geometry or computed from the positions) through its instance matrix into a world sphere (ws/cull). Instance `flags` (float 25, `VSOut.flags`) carry `receiveShadow: false` in bit 0 (ws/shadows); the other bits are reserved.

**Animation.** Clips are data, sampling is arithmetic, and the renderer sees only matrices: a mixer blends keyframe clips into a pose, the pose resolves into node world matrices for anything that follows a bone (cosmetics on sockets, a weapon in a hand) and into joint matrices for skinning (E-015). *Today (ws/anim):* `@thunderclap-engine/engine/anim` (`anim/`) is pure TypeScript with no GPU and no `render/` import. `AnimationClip { name; duration; channels; events? }` and `AnimationChannel { node; path: 'translation' | 'rotation' | 'scale' | 'weights'; interpolation: 'STEP' | 'LINEAR' | 'CUBICSPLINE'; times; values }` carry glTF sampler semantics one to one (cubic-spline in/out tangents, hold outside the key range), so the glTF importer fills them without conversion. `sampleClip(clip, t, pose, weight, blend, cursor?)` writes into a `Pose` (10 floats per node: `t3 q4 s3`, `POSE_NODE_FLOATS`) by override (lerp/slerp) or additive (deltas) blending, with a per-channel keyframe cursor so forward playback is O(1) amortised. `Skeleton { parents; rest; inverseBind?; joints? }` is parent-before-child; `poseToWorld(skeleton, pose, out)` writes 3×4 row-major world matrices in the `render/transform.ts` convention (12 floats per node, `WORLD_NODE_FLOATS`), and `skinMatrices(skeleton, world, out)` writes `world[joint] · inverseBind` in the same 12-float-per-joint layout `render/skin.ts` uploads (glTF 16-float column-major inverse bind matrices are converted on the fly; `inverseBindFromRest` builds them for procedural rigs). `AnimationMixer(skeleton)` holds a fixed pool of `AnimationAction`s: `play(clip, { layer, weight, loop, speed, fadeIn, blend, startTime })`, `crossFade(from, to, seconds)` (effective weights sum to 1 throughout), `stop(action, fade?)`, `update(dt)` → `mixer.pose` (per layer ascending: override actions averaged by weight and lerped on by `min(1, Σ)`, then additive actions), and `onEvent(cb)` for `clip.events` crossings, once each, across loop wraps. Quaternion helpers (`quatSlerp`, `quatNlerp`, `quatMultiply`, `quatFromEuler`, …) work in place on flat arrays. Sockets (ws/sockets) attach cosmetics to joints: `createSocket(skeleton, joint | name, { position, rotation, scale })` (names through `Skeleton.names`) gives a `Socket { joint; offset }`, `socketWorld(socket, world, instanceWorld, out)` writes `instance · world[joint] · offset`, and `attachTransform(...)` puts it into a `Transform` (`Transform.setMatrix`) so the attached mesh draws through `frame.mesh` unchanged. `createAnimGraph(mixer, desc)` (ws/anim-graph) puts a state graph over the mixer: states hold a clip or a 1D blend space whose two nearest points share the weight with one synced phase across their clips, transitions carry a condition over a shared parameter object, a fade and an optional exit time, and every state's weight lerps toward the target so the weights sum to 1 throughout. Nothing allocates per frame after setup. IK and root motion (ws/ik) are pose arithmetic between sampling and the final `poseToWorld`: `twoBoneIk` (analytic, pole vector, weight) and `lookAt` (forward axis, up hint, angle clamp) read the sampled pose's world matrices and write local rotations, and `extractRootMotion` splits a clip into an in-place clip and a `motion` clip whose `applyRootMotionDelta` gives the game a heading-frame position delta and a yaw delta, loop wrap included. *Today (ws/retarget):* `createRetargetMap(source, target, { pairs?, match?, rootNode?, scaleTranslation? })` pairs the joints of two skeletons (explicit pairs, exact names, then a lowercase separator-stripped compare of `Skeleton.names`; leftovers in `map.unmatched`) and precomputes per target joint the two rest-frame quaternions `pre`/`post` with `Rt = pre · Rs · post`, the source joint's rest-relative delta in its parent frame carried into the target parent's frame; `retargetPose(map, sourcePose, targetPose)` applies them with no allocation (translations stay at the target rest except the root's, scaled by the hip-height ratio), and `retargetClip(map, clip, { sampleRate?, name? })` bakes a clip to the target once. Morph targets (ws/morph) blend on the CPU: `createMorphBlender(base, targets, layout)` → `MorphBlender` writes `base + Σ weight × delta` into the position and normal lanes of an interleaved vertex buffer (normals renormalised) and reports whether anything changed since its last apply, so a mesh uploads through `Mesh.update` only on a change; `sampleWeights(clip, node, t, out)` samples a `'weights'` channel with `sampleClip`'s rules. ws/anim-4 adds 2D blend spaces and pose-matched transitions to the graph, `applyAimOffset`, `applyFootIk` and `updateSpringChain` as further post-mixer passes over the sampled world matrices, and `compressClip` / `quantizeClip` for load-time clip size. ws/assets-4 adds `skinPose(skeleton, source, palette, slot, dt?, world?)`: the mixer update, `poseToWorld`, `skinMatrices` and `SkinPalette.write(slot)` in one allocation-free call (the palette typed structurally, so still no `render/` import). *Planned:* full-body IK when a game names them.

**Tweens.** Every game moves numbers over time: a menu slides in, a camera eases to a target, a hit flash fades. The engine owns the arithmetic and the bookkeeping, not the clock. *Today (ws/tween):* `@thunderclap-engine/engine/tween` (`tween/`) is pure TypeScript with no GPU and no import outside itself. `createTweens()` returns a `Tweens` manager a game ticks with `update(dt)` from its frame or update hook; it holds root tweens in one array, compacts it in place, and allocates nothing after setup. `to(target, props, seconds, opts)` animates number fields by dotted path (`'x'`, `'position.0'` into a `Float32Array`, `'style.opacity'`), resolving the paths to holders and keys when the tween is created and reading start values when it starts, after its delay; `value(from, to, seconds, onUpdate)` reports one number; `delay(seconds)` is a gap or a timer; `sequence(...)` and `parallel(...)` are tweens of tweens that carry a child's leftover `dt` into the next child, so a long frame drifts nothing. `TweenOptions` carry `ease`, `delay`, `loops` (`-1` forever), `yoyo` (groups play their children backwards), `onStart`/`onUpdate`/`onComplete` and `timeScale`; the `Tween` handle has `progress`, `elapsed`, `duration`, `pause`/`resume`, `kill`, `restart`, `then(fn)` and `promise()`. A tween killed or created from a callback inside `update` is safe. The easing table `ease` holds the Penner set (`quad`…`bounce`, `In`/`Out`/`InOut`), `linear`, `smoothstep`, `steps(n)`, `cubicBezier(x1, y1, x2, y2)` and `spring(stiffness, damping)`: a `SpringEase` is a description, not a function of `t`, and a tween given one has no duration, integrates the spring in bounded substeps and completes when it settles. `post/blend.ts` imports `Ease` and the four functions it used to define from here (`easeLinear`, `easeIn`, `easeOut`, `easeInOut` stay as aliases), so there is one easing table. *Planned:* nothing on spec; colour-space interpolation when a game asks for it.

**Navigation.** Finding a way is arithmetic over the game's own map, and the renderer never hears of it: a grid of walkable cells with costs, a search that fills a path the game follows, a flow field that one build serves a crowd with, and steering that keeps agents apart. Navigation is 2D over world `x` and `z`; height is the game's business (sample the terrain when placing the agent). *Today (ws/nav):* `@thunderclap-engine/engine/nav` (`nav/`) is pure CPU with no import from any other engine module and no allocation per query after warm-up. `createNavGrid({ width, height, cellSize, origin?, walkable?, cost? })` gives a `NavGrid` (`costs: Float32Array`, 0 = unwalkable; `setWalkable` / `setCost` bump `version` on every real change; `toCell` / `toWorld`). `findPath(grid, from, to, out: NavPath, opts?)` is A* with a binary heap over per-grid scratch arrays (a `WeakMap`), octile heuristic, step cost `(1 | √2) × cost(dest)`, no corner cutting (a diagonal needs both orthogonal neighbours walkable), and `maxExpand`; it writes world-XZ cell centres into a `NavPath { points: Float32Array; length; cursor; version }` stamped with `grid.version`, so a changed wall marks the path stale. `smoothPath` string-pulls it in place over `hasLineOfWalkable` (an integer supercover line). `followPath(path, position, speed, arriveRadius, outVelocity)` returns `'moving' | 'arrived'`. `createFlowField(grid).build(goals)` is Dijkstra from the goals into `distances` and unit `directions` per cell (`directionAt(worldX, worldZ, out)`). `steer.separate`, `steer.arrive` and `steer.avoidDisc` write velocities. `harness/nav.html` (no WebGPU) and `e2e/nav.spec.ts` prove a path around a wall, rerouting on a toggled wall and 32 agents arriving within a bound of fixed-step sim time on every matrix row. *Today (ws/nav-2):* for non-grid worlds, `bakeNavMesh` voxelises world triangles Recast-style into a `NavMesh` of convex polygons with 3D heights, `findMeshPath` is polygon A* with funnel string pulling into a `NavPath3` that names the off-mesh links (`addOffMeshLink`) it takes, `createCrowd` is ORCA local avoidance and `exportNavMesh` / `importNavMesh` let a game bake at build time and ship bytes (`harness/navmesh.html`, `e2e/navmesh.spec.ts`). *Today (ws/nav-3):* the grid takes an `edgeCost(from, to)` hook (`Infinity` blocks one way) and a `neighbours: 4 | 8` setting that every search follows, `reachable(grid, start, budget)` fills a reusable `Reach` (distances, parents, `pathTo`) for move-range queries, index edits mark a `FlowField` `stale` for an in-place `update()`, a field seeds from several `goals`, and `findPath` takes `maxCost` and `heuristicWeight`. *Today (ws/nav-4):* a mesh polygon carries an area byte that a query prices or excludes (`areaCost`, `areaMask`; stamps at bake or `markArea`), an `ObstacleSet` stamps moving discs and boxes onto the polygons or a grid cost layer in one `apply()`, a `PathQueue` spends a fixed pop budget per frame over ticketed requests, a `Corridor` funnels the remaining polygons under a crowd agent attached to the mesh (`Crowd.attach`, `setTarget`, replans when the mesh version moves) and `createFlowField3` gives a horde an O(1) direction per polygon. *Today (ws/nav-5):* `reachable(mesh, from, { budget, areaCost?, areaMask?, maxPolys? })` is the mesh move-range query (a budget-bounded Dijkstra with `findMeshPath`'s cost model into a reused `MeshReach`) and `reachableOutline` traces its boundary loops; `NavPath3.cost` reports a path's priced cost, `loadNavMesh(bytes)` validates a shipped bake, and `pnpm bake:nav <input> <output>` (`scripts/bake-nav.mjs`) bakes one source to one format-2 file. *Today (ws/nav-6):* `NavBakeOptions` needs only `cellSize` (the rest default from it through `resolveNavBakeOptions`), a bad option throws a `NavBakeError` naming it, and a bake whose triangles give no polygon warns once instead of returning an empty mesh silently. *Planned:* voxel-column grids when a game names them.

**Networking.** A networked game talks to an authoritative server through a protocol the engine owns at both ends: the envelope (handshake, liveness, commands, live queries, entity stream, predicted input, bulk lane) is engine-owned, the game fills its roles with its own types, and one hash of the whole schema is checked at the handshake. The engine opens no connection (VISION rule 4): the game hands in a `Connect`. *Today (ws/net, C9, E-042):* `@thunderclap-engine/engine/net` (`src/net/`, no DOM, runs in Node for bots) is the client half. `defineSchema` builds the hashed schema (canonical text, SplitMix64 hash, `src/net/testdata/schema.json` the parity vectors for the Rust side); `createNet` is a session with handshake, ping and dead-link detection, reconnect with backoff, commands, live queries patched in place and resumed after a reconnect, interest, the entity stream (`EntityStream`, changed fields only, key frames on demand) and the bulk lane. `SnapshotBuffer` interpolates other things on an adaptive delay with no per-frame allocation, `Predictor` predicts the driven thing and replays in-flight inputs on a correction, `Optimistic` rolls a refused edit back to the last confirmed value, `NetClock` tracks server time. `inPagePair` and `inPageHub` are in-page transports with live latency, jitter and loss, and `ServerEnd`, `QueryFeed` and `EntityEncoder` the TypeScript server half for tests and in-page authorities; the real server is `tc-net`. `harness/net.html` runs two clients against an in-page authority.

**Renderer.** The renderer records draws into a `Frame` and draws them for one camera into one target; it owns no camera and no frame of its own beyond conveniences. *Today:* `renderer.beginFrame(time, dt)` returns the reusable `Frame`; `renderer.render(frame, camera, target = renderer.target)` encodes one scene pass of the recorded draws for that camera into a `SceneTarget` (colour + emissive, `SCENE_FORMAT`, plus a `depth24plus` attachment made on first use by a depth camera); `renderer.endFrame()` runs post (or present) from `renderer.target` and submits, and calls `render(frame, renderer.camera)` itself when nothing rendered in between, so `createGame`'s single-camera path is unchanged. Several `render` calls per frame (split screen through `camera.screen`, which sets the viewport and scissor as a fraction of the target when it lies inside the unit square, else in logical px; UI over world through layers; an offscreen view through `renderer.createSceneTarget(desc)`) share one instance buffer at increasing offsets and one 2032-byte uniform buffer (globals, camera, lights) plus bind group per view (`engine-globals`, `engine-globals-1`, …; pooled, so steady state allocates nothing); the first view into a target clears it (colour from `frame.clearColor`, depth to 1), later views load. A view that sees a `Drawable` with `readsDepth` splits its scene pass at the opaque/blended boundary, copies the depth attachment into `SceneTarget.depthCopy` and calls the drawable's `afterOpaque(encoder, view)` before the blended pass, so depth-reading drawables (water, soft particles, decals) see this frame's opaque depth; frames without one encode exactly the passes they did before (ws/render-hooks). `renderer.stats` is reset in `beginFrame` and summed over the views. Each view's `view_index` is its camera's `viewIndex` (default 0), so a stereo pair is two `render` calls with `screen` the two halves and `viewIndex` 0 and 1 (ws/two-views; `harness/views.html` and `e2e/views.spec.ts` prove it on the matrix, with depth cleared once per target and each half's draws scissored to it). `Renderer.render` outside `beginFrame`/`endFrame` throws. Materials bind texture arrays: `TextureDesc.layers` makes a `'2d-array'` view, `loadTextureArray(device, sources, { mips })` uploads one image or pixel source per layer and builds the mip chain on the GPU (`generateMipmaps`, a cached blit pipeline per format, also for 2D textures made with `mips: true`), `viewDimension: '2d-array'` on a `MaterialDesc` or `FullscreenPassDesc` declares the slot as `texture_2d_array<f32>`, the `'linear-mip-repeat'` and `'nearest-mip-clamp'` samplers blend mips, and a 3D mesh carries a face's layer in its vertex colour's alpha (`harness/stream.html`; ws/texture-array). `loadTexture` builds a mipmapped 2D texture in one call and `defaultTextures(device)` supplies white/black/flat-normal/metal-rough/checker; every unset material slot binds white (ws/texture-registry). With `camera.cull` (the perspective default) a render call drops, before sorting, every mesh draw whose world sphere is outside one of the camera's six cached `frustum` planes and counts it in `renderer.stats.culled`; sprites, drawables and meshes without bounds are never culled, and the 2D path (`cull` off) is untouched (ws/cull). `endFrame({ present: false })` (ws/xr) skips the post or present step into the swapchain and only submits: an XR frame's eyes went to the session's layer and nothing goes to the canvas; when nothing rendered (a frame with no views) it submits nothing rather than rendering `renderer.camera` into the page target, and a `beginFrame` while a frame is open (the last one threw) drops that frame unsubmitted (ws/xr-fixes). `renderer.resolve(target, out, viewport?)` (ws/xr-post) is that post or present step for any target and any output view, inside the frame after a `render`: it runs `renderer.post` (or the built-in present) from `target` into `out`, confined to `viewport` (texture px, loading the rest) when given, and consumes the target so its next `render` this frame clears again. The XR step is `render(frame, eye.camera, surface.scene)` then `resolve(surface.scene, eye.target.color.view, eye.viewport)` per eye on the one encoder, so both eyes share one HDR target and the post stack's intermediates. `PostProcessor.encode(encoder, inputs, output, viewport?)` carries the viewport and a processor sizes itself to its inputs (`PostStack` resizes once when they change). `PostInputs.depth` and `PostInputs.projection` (`PostProjection { near, far, proj }`, ws/post-depth) hand the post processor the target's depth attachment and the projection of the camera that drew it, `null` on frames that rendered no depth, so depth passes can skip without touching the 2D path. Many instances of one mesh and material go through `frame.meshes(mesh, material, batch)` (typed arrays copied straight into the frame's upload, one sort key, culled per instance or as one sphere) or a retained `InstanceList` (`renderer.createInstanceList`, `frame.list`: its own vertex buffer, dirty-range uploads, swap-remove), so 50k cubes cost a few ms of CPU instead of one `frame.mesh` each (ws/batch-submit; `docs/BENCH.md`). *Today (ws/ergo-2d-2):* a `TileLayer` in `order: 'painter'` is one mesh per diagonal drawn back to front at `base + col + row`, optionally on an `Iso` lattice (`geom/iso.ts`) with per-tile elevation, and `depthOf(tx, ty, elev)` is the `order` a sprite takes to sit between its tiles; `createParallax` offsets tile layers by `camera × (1 - factor)` wrapped at a period, and `createFollow2D` (dead zone, look-ahead, smoothing, bounds) drives an ortho2d camera through `x` and `y` only. A target may carry aux attachments beside colour and emissive (`SceneTargetDesc.aux`: an `rg8unorm` roughness/metalness and an `rg16float` velocity target written by materials that declare `aux`, moving instance lists and skinned palettes with history), the camera keeps last frame's matrices and a jitter the post processor must ask for, and post reads all of it through `PostInputs.view`, `roughMetal` and `velocity` (ws/render-4). `frame.mesh` also takes a `MeshLod` (geom's `LodChain` with its meshes) and picks a level per instance from its projected size, with hysteresis and one draw per non-empty level; `uploadKtx2` puts a KTX2 file on the GPU in its own block format when `renderer.caps.compressed` has the family (no transcoder); and a material may name a `shadowFragmentEntry` so its discards (the standard material's dissolve) cut its shadow too (ws/render-5). `frame.meshes` and `InstanceList` take a `MeshLod` too, bucketing their instances into one draw per level with level memory kept per view, the standard material's alpha mask cuts its shadow, `renderer.setJitter(fn)` jitters every view's camera with the renderer keeping the history, and `initGpu` requests the adapter's compression features (ws/render-6). An `InstanceList` instance may carry a stable key that its LOD level and velocity history follow across reorders, and copied batches (LOD lists with velocity, `frame.meshes` with `prevMatrices`) write per-instance motion through one shared previous-matrix lane (ws/render-7), and so do single `frame.mesh` draws from each `Transform`'s previous world matrix kept per view (ws/render-8). A LOD list's flush uploads nothing, since only its per-level copy is drawn, and the test fake GPU holds buffer bytes, rejects missing `COPY_SRC`/`COPY_DST`/`MAP_READ` flags and maps staging buffers for real (ws/render-9). Every pipeline drawing into a scene pass takes its colour targets from `renderer.sceneTargets(blend, frame.auxKey)` and is keyed on the view's target set, so drawables validate in aux targets (ws/render-10). Billboards and world particles write their own motion into a velocity attachment (a `:motion` pipeline variant, alpha-blended; billboards keep last frame's drawn anchors, world particles step back by `sim.dt`), XR eyes get `createGame({ aux })`'s set through `XrSurfaceOptions.aux` with each eye's own previous view-projection, and `skinPose` refuses a `SkinPalette` (`jointCount`) too small for the skeleton (ws/render-11). The v1 surface (ws/api-render, E-036) keeps the block offsets and shader sources only tests read internal (off the entry since 1.0.0), names the blend type `RenderBlendMode`, the sun's direction `direction`, render's fog `DistanceFog`, and adds `createSpriteMaterial({ texture })`, uniform `setScale(s)`, `createMeshLod`, `SkinPalette.write`/`params`, `atlasFrames` `inset` and the z = 0 `screenToWorld(sx, sy, out)`.

**Retained core.** *Today (preview, ws/core-retained, D1 §3):* `src/render/core/`, exported from `@thunderclap-engine/engine/render` beside the immediate path, which it does not change. `createRenderCore(gpu)` holds arenas (`Arena`: GPU buffers carved into free-listed ranges, any vertex stride, the shared `QuadIndex`), draw sets (`DrawSet`: one pipeline's slots, each a mesh range, an instance range and a bounding sphere) and the pass list (`depthPre`, `opaque`, `cutout`, `transparent`, `overlay`; a pass encodes only when it has work, and depth exists only when a running pass tests it). `core.prepare(encoder, views)` writes the views (a list, one for now), uploads only dirty slot ranges and runs one compute cull per frame that writes each slot's `drawIndexedIndirect` arguments per view (a CPU twin for small sets); `core.draw(encoder, view, target)` replays cached render bundles of those indirect draws, or one `multiDrawIndexedIndirect` per set where the device has Chromium's feature. Instances bind per slot with a ranged `setVertexBuffer`, so WebKit (no `indirect-first-instance`) runs the same path. A held frame is a flat number of GPU calls, 9 at both 1,500 and 6,000 meshes, with no allocation (`core.test.ts`, `harness/core.html`, `e2e/core.spec.ts`). The fake GPU (`src/render/fake-gpu.ts`) records bundles, indirect draws, indirect dispatches and debug markers, and counts every call (`FakeDevice.calls`).

**Lighting.** The engine supplies light uniforms; the style (Lambert, toon, rim, none) is the game's WGSL, so a candle-lit dungeon and a sunlit overworld are two fragment shaders over one block. *Today (ws/lights):* `Lights` in `render/lights.ts` (ambient rgb, `sun { dir, color }`, `points: PointLight[]` of `position`, `color`, `radius`; `MAX_POINT_LIGHTS` = 16) is carried by the frame as `frame.lights`, which the game sets or mutates and which defaults to the unlit block (ambient 1, no sun, no points). The renderer writes it as `EngineLights` at `@group(0) @binding(2)` (snake_case: `ambient`, `point_count`, `sun_dir` normalised and pointing the way the light travels, `sun_color`, `points[16]` of `position`, `radius`, `color`, then `sun_view_proj`, `shadow_params` (bias, texel size, enabled), `fog` (rgb, density), `fog_range` (near, far), then `spot_count`, `sun_layers`, `point_layers[4]` (vec4u) and `spots[8]`; `LIGHTS_BLOCK_FLOATS` = 316) at byte offset 768 of each view's uniform buffer, in the same upload as the globals and the camera block (one buffer per view, 2032 bytes), and `renderer.globalsLayout` has the binding for every material and drawable, plus the sun's shadow map (`texture_depth_2d`, binding 3) and a comparison sampler (binding 4). `materialPrelude` declares the block plus `engine_point_lights(normal, world_pos)` (Lambert × `(1 - d/radius)²`), `engine_shadow(world_pos)` (3×3 PCF against the map; 1 when none), `engine_fog(color, world_pos)` (linear or exponential by distance from the eye; identity at density 0) and `engine_lambert(normal, world_pos)` (ambient + sun Lambert × shadow + points), which a material may call or ignore; with the default block `engine_lambert` is `vec3f(1)`, so `fs_main` contracts are unchanged and the 2D path is pixel-identical. *Shadows (ws/shadows):* `Lights.sun.shadow: SunShadow` (`extent`, `size` 1024/2048/4096, `near`, `far`, `bias`) makes the renderer encode one depth-only pass per `render` before the scene pass, through `render/shadow.ts` (`ShadowMap`: a `depth32float` map, an orthographic `Camera` centred on the view camera's position and pointed along the sun, a pipeline per vertex layout reusing the prelude's `vs_main`), over the view's opaque draws with `castShadow` (default: 3D layouts yes, `VERTEX_LAYOUT_2D` no, so 2D frames never run it); the shadow list is culled against the sun box, not the view frustum (`stats.shadowDraws`); a 1×1 depth placeholder is bound until the first shadow pass (after it the last map stays bound and `shadow_params.z` = 0 makes `engine_shadow` return 1), so one layout serves both. `receiveShadow: false` is instance flag bit 0 (`VSOut.flags`) for materials to read. `Lights.fog: Fog` (`color`, `density`, `near`, `far`) feeds `engine_fog`. `Lights.writeBlock(f32, u32, offset, shadow?)` allocates nothing; `harness/mesh.ts` lights its scene with a shadowing sun, fog and a circling point light. *Spots and masks (ws/spot-lights):* `Lights.spots: SpotLight[]` (`position`, `direction`, `color`, `radius`, `innerAngle`, `outerAngle`; `MAX_SPOT_LIGHTS` = 8) and an optional `layers` mask on every light are appended to the block after fog, the instance's low 23 layer bits ride in the flags float above the shadow bit (`packInstanceFlags`), and the prelude gains `engine_light_accum(world_pos, normal, layer_mask)` (sun × shadow + points + spot cones of the lights whose mask shares a bit), `engine_lambert_layers` and `engine_instance_layers(flags)`, with `engine_lambert` unchanged in signature and spanning every layer; `harness/lights.html` sweeps a spot beside a masked point light. **Materials.** `createStandardMaterial` (`render/standard.ts`, ws/pbr) is the one material a game needs before writing WGSL: glTF metallic-roughness PBR over the same lights block, with `WGSL_PBR` exposing its BRDF and derivative-based normal mapping to custom shaders; since ws/pbr-lights the Lambert helpers and the PBR material run one generated light loop (`wgslLightLoop(name, brdf)`: sun × shadow, points, spot cones and layer masks, with the BRDF expression inlined because WGSL has no function pointers), so every light the prelude sees, every material sees. *Planned:* cascades when a game needs them.

**Frame loop.** `GameLoop` runs a fixed 60 Hz update and a variable render; the camera and the target are inputs to the render path (`Scene.render(frame, camera, alpha)`, `renderer.render(frame, camera, target)`), not state read from the renderer. The host decides who schedules frames (rAF, Electron, `XRSession.requestAnimationFrame` through `createXrHost`); `GameLoop.setFrames(src)` swaps the source while running (ws/xr). *Today:* `GameLoop` and `FixedStepper` in `core/loop.ts` (fixed step, `maxFps` cap, pause) call `render(alpha, time)` from the frames of a `FrameSource` (`GameLoopOptions.frames`: `createGame` passes its `Host`; the default is `defaultHost()`, read on the first `start()`; tests pass a stub they step by hand). A frame that throws still schedules the next before the error reaches the frame source, and so does a throwing clock (`now()` is read inside the same try, #7), and `maxFps` is ignored for a `kind: 'xr'` source (ws/xr-fixes). The loop never calls `requestAnimationFrame` itself. The game's render callback records a `Frame` and calls `renderer.render(frame, camera, target?)` per camera (or lets `endFrame` render `renderer.camera`). With `GameLoopOptions.fixed: false` (what `createGame({ sim: false })` uses) there is no accumulator: `update(dt, time)` runs once per rendered frame with the real clamped delta, `render` gets `alpha` 1, and pause still skips update. `Scene<Ctx, Frame, Cam = Camera>` and `SceneStack` in `core/scene.ts`: `Scene.render(frame, camera, alpha)` takes the camera from the game (`SceneStack.render(frame, camera, alpha)` forwards it), so no scene reads `renderer.camera`; `createGame` passes `ctx.camera` and then calls `renderer.render(frame, ctx.camera)` itself (ws/plumbing, E-010). `Scene.preload?(ctx)` makes `push` / `replace` async (they return a promise; the old top keeps running and later ops queue while it is pending, `stack.onTransition` reports `'preload' | 'enter' | 'exit'`), and `core/` also holds the engine's deterministic utilities, none importing outside `core/`: `createRandom` (seeded xoshiro128** with named forks), `createNoise` (Perlin, simplex, value, fbm), `createScheduler` (timers and cooldowns on the game's `dt`) and `createPool` (ws/core-2), and `hash2` / `hash3` / `hash2f` / `hash3f` (`core/hash.ts`, ws/core-3): a pure uint32 or [0, 1) float per integer lattice cell under a `Seed` hashed like `createRandom`'s, which the demos and templates use for their per-texel and per-column rolls instead of hand-rolled hashes.

**Host.** `interface Host extends FrameSource { kind; requestFrame; cancelFrame; openExternal; copyText; clipboardWriteAllowed; fullscreen; storage; window?; embed }`. Implementations: `web` (detects iframe vs top and wraps today's D-036 link service) and `electron` (preload bridge). The engine never calls `window.open`, `navigator.clipboard` or `localStorage` directly. *Today:* `host/` (`@thunderclap-engine/engine/host`) has the `Host` type, `createWebHost({ win? })` and `defaultHost()` / `setDefaultHost()`. `clipboardWriteAllowed()` says whether `copyText` can write without a prompt; `fullscreen` is `{ available, active, toggle, watch }` and `storage` is `{ kind, open(): StorageLike | null }`. `save` (`createSaveStore`, `listSlots`), `persistMixer` and the `externalLink` widget take `host` and default to `defaultHost()`. `window.open`, `navigator.clipboard`, `execCommand` and `localStorage` appear only in `host/web.ts` and `host/web-links.ts`; the fullscreen DOM calls stay in `platform/device.ts`, which the web host wraps. The Electron host lives in this repo as `packages/host-electron` and provides `createElectronHost()` (`@thunderclap-engine/host-electron`): the same interface over the preload bridge `window.thunderclap`, `kind: 'electron'`, storage the renderer's `localStorage` (served from the fixed origin `app://bundle`), and `window` with `close`, `minimize`, `toggleMaximize` and `setTitle`. A game installs it with `setDefaultHost` or passes it to its ctx; the engine never imports it. The installable web shell is `packages/host-pwa` (`@thunderclap-engine/host-pwa`, ws/host-pwa): `createPwaHost()` wraps the web host (`kind` stays `'web'`) and adds a typed `host.pwa` extension (install prompt, update prompt, offline flag, cache status), while `pwaPlugin` (`@thunderclap-engine/host-pwa/vite`) emits the manifest and service worker at build time, so the engine itself stays network-free. Frames come from the host (ws/render-call, D-044): `FrameSource { requestFrame(cb: (timeMs) => void): number; cancelFrame(handle) }`, wrapped over the window's `requestAnimationFrame` on web and Electron; `GameLoop` schedules through it, so an XR session is a `Host` implementation (`XRSession.requestAnimationFrame`), not a redesign: `createXrHost(session, base)` (ws/xr) returns an `XrHost` (`kind: 'xr'`) whose frames come from the session, which exposes the current `XRFrame` on `frame` during a callback, and which delegates everything else to the page host; `createGame({ xr })` moves the loop onto it with `loop.setFrames` on `ctx.xr.enter()` and back on exit or the session's `end` event. Three optional facets serve a phone shell and the browser alike (ws/host-mobile): `lifecycle` (`state`, a getter: `'active' | 'background'` (ws/core-8, E-036), `watch`; `createGame` stops frames and flushes the save on `background`, restarts on `active` and calls `hooks.lifecycle`), `haptics` (`available`, `impact`, `notification`, `vibrate`; `navigator.vibrate` on the web) and `safeArea` (`insets()` in CSS px, `watch`; `createGame` pads `ui.layout` through `followSafeArea`), and `packages/host-capacitor` (`@thunderclap-engine/host-capacitor`, `kind: 'capacitor'`) fills the interface from Capacitor's plugins handed in at construction (browser, clipboard, screen orientation, a Preferences-backed `storage`, `appStateChange` lifecycle, native haptics, an Android `back` watcher), never importing them.

**Input.** The action map for keyboard, mouse, touch, pen and gamepad, with `blocked()`, `lastDevice`, queued taps, iframe-safe `preventDefault`, injectable pads and public feed methods for tests; `ui/padnav.ts` drives modal panels from the pad and `ui/menu-nav.ts` (`menuNav`) drives non-modal menus. `Gestures` (`input/gestures.ts`) recognises tap, double tap, long-press (450 ms), pan, drag (with its origin) and pinch (scale) from pointer events, with thresholds in CSS px (pan 10) and positions in game space through the same `PointerTransform`; while two or more pointers are down, pan and drag report nothing (a second pointer cancels them and starts the pinch, ws/plumbing). It reports per tick like `Input`: one discrete gesture per kind per tick (extras queue), continuous ones every tick from `start` to `end` or `cancel`; travel is cumulative from the down point and the pan threshold is checked before the long-press timer on every move, so a slow drag under a long frame pans and never long-presses (ws/gesture-longpress), and `gestures.onGesture(listener)` observes each recognition synchronously, for tests and logging rather than game logic. `input.setGestures(g)` (or the `gestures` constructor option) links it: the gestures share `blocked()` and the transform, attach with `Input.attach`, advance in `Input.update()`, and can be bound as actions (`{ gesture: 'tap' | 'doubleTap' | 'longPress' | 'pan' | 'drag' | 'pinch' }`), so a game can map tap to `select` and long-press to `info` without reading gestures; `createGame` builds the `Gestures` (`CreateGameOptions.input.magnify` is its `magnify`) and exposes them as `ctx.gestures`. While blocked nothing is reported and a running pan, drag or pinch gets one `cancel`. The `magnify` option (`input/magnify.ts`, ws/port-altar) is loupe and snap for small touch targets: while one touch pointer is down each tick reports `gestures.aim`, the finger raised by `lift` (56 CSS px) while it drags, snapped by the game's `snap(x, y)` (usually `snapToGrid`, the nearest accepted cell within half a pitch), and while `pitch()` is below `below` (44 CSS px) a `Loupe` beside the finger magnifies the aim point `zoom` (2.5) times with the target ringed. The aim the finger lifted at is reported once more (`ended`) on the drag's `end` tick, so a dragged thing lands where it was aimed. Mouse and pen never aim. **Quality.** *Today (ws/intents-quality, D1 §2.12):* `@thunderclap-engine/engine/quality` holds `detectTier(readDevice(gpuInfo(adapter)))`, a starting `low`/`medium`/`high` tier with its reason (software adapter, headset or Adreno → low; `maxTextureDimension2D` under 8192 or two honest cores → medium), and `createGovernor({ rungs })`, one frame governor that sheds and restores work through registered `Knob`s (`{ name, step(down), cost? }`; `toggleKnob`, `stepKnob`, `dynamicResolutionKnob`) so modules never adapt on their own and fight. An attached head-locked or billboard panel places itself again in `prepare` from the camera it follows, so in VR it tracks the head as drawn (ws/xr-fixes). ws/ui-4 gives world-anchored UI one frame and one pad latch: `Anchors.frame` and `anchors.project` are what tooltips, the world cursor and the pooled `ui.floats` project through, `PanelStack.padOwner`/`onPadOwnerChange` is the modal-has-the-pad latch `PadNav`, `ui.cursor` and the game's bindings (`ui.padOwner`) share, world panels `attach(input)` to poll on `input.onUpdated`, and `ui.ring` and `ui.compass` complete the action HUD. ws/ui-5 adds the orb meter (`ui.meter({ shape: 'orb' })`, with a damage `trail` shared with the bar), floating text through the same anchors (`createFloats(ui, camera)`, pooled, culled behind the camera, stacked and crit-popped) and a canvas minimap (`createCanvasMinimap`, round or square, north- or player-up, redrawn only on change, `onPick` in world units). ws/ui-6 makes them the only ones: `ui.floats(camera?)` is the overlay's `Floats` pool and `ui.minimap(opts)` the canvas map (with `worldRadius`, rim clamp read back through `markerAt`/`rim`, and `place` per form factor), and ws/ui-4's DOM float numbers and minimap are gone. Since ws/ui-7 `layout` warns once when a widget overflows its region (`layout.overflows()`), and minimap markers can carry a `heading`; `LayoutSpec.bars` sizes the bars (ws/ui-8) and side rails (ws/ui-9) to their content, the larger one taking a shared corner, rails measured at `max-content` (ws/ui-10), and `ui.meter({ size })` takes a size per form factor; a re-layout moves only widgets out of place and tells them through `onMove`, so `ui.meter({ place })` follows the form factor live (ws/ui-11). ws/ui-spec adds UI written as data (`ui/spec/`, from Forge Wilds' spec framework, game nouns out): a `PanelSpec` of words bound to model keys with `b(key)` is compiled once to typed arrays; `SpecModel` marks changed keys and dirty row fields; `SpecBoxes` is a pure two-pass layout that allocates nothing once warm; `panel(spec).apply()` returns at once when idle; `presentDom` draws one real element per word (buttons, inputs, `role=meter`, tablists, pooled list rows with `data-tc-id` control ids for `PadNav`) and writes only what changed; `hud(spec)` + `presentHud` place panels through `ui.layout` and `presentModal` opens one on `ui.stack`; the look is `theme(tokens)` as `--tcs-*` properties. The existing widgets and `ctx.ui` are unchanged.

**Streamed voxel sections (ws/voxel-data, E-041).** The CPU and Worker half of a streamed block world for any block game, generalized from Forge Wilds' mesher; the renderer half is C2's. Game rules are data, never engine nouns. *Today:* in `voxel/`, `defineVoxelFormat` bundles a `BlockTable` (`defineBlockTable`: per id a face class `none`/`opaque`/`liquid`/`cutout`/`foliage`/`cross`, light cost, emission and one of eight hues, inset, cross quads, constant vertex fields), a `VertexSchema` (`defineVertexSchema`: a declared bitfield over 2 × u32 with the engine's `x y z face ao sky block id` and the game's fields; `vertexSchemaWgsl` generates the matching `decode_voxel_vertex` include, no `override`) and a `CellLayout` (where the id sits in a u32 cell, which bits reach the vertices). `createSectionStore` keeps sparse sections by a 53-bit `sectionKey` as their encoded bytes (decoded through the game's `SectionCodec` only to edit), knows readiness (all 26 neighbours known), hands dirty ready sections out nearest the interest point first, returns from `edit` every section whose mesh changed, and packs self-contained transferable `SectionJob`s. `SectionMesher` (in a Worker via `installSectionMesherWorker`, fed by `SectionMeshPool`, which builds a job only when a port has room and survives throwing jobs and dying Workers) emits opaque, liquid and foliage streams with Forge's AO, smooth sky light and greedy merge rules, block light by `BlockLightFlood` (Dial's algorithm over the 27 sections around a job, seamless for sections ≥ 15), and Checchi face-pair connectivity (`ConnectivityFlood`). `raycastCells` / `sectionRayProbe` pick through the store, stopping at unloaded sections. Zero allocations on the page per frame: the store and pool allocate per job or edit, not per frame; the mesher reuses its buffers per thread. Tests port Forge's mesher, light and pool tests and mesh a non-Forge table (`src/voxel/section-mesher.test.ts`, `section-store.test.ts`, `schema.test.ts`). The bounded demo grid (`createVoxelGrid`, `createVoxelChunks`) is unchanged.

**Localisation.** `i18n/` (ws/i18n) ships a game in several languages with no dependency and no network: `createI18n({ locale, fallback, tables, missing, onMissing })` holds one string table per locale, inline or behind a loader the game supplies (`() => import('./ru.json')`), parses every string once into an AST per dotted key (ICU-style `{name}`, `{n, plural, …}` with `Intl.PluralRules`, `=N` forms and `#`, `{g, select, …}`, `{n, number}`, `{d, date}`; errors name the key and column) and formats on `t(key, args)` allocating only the output string, looking the key up along a chain (the locale, its language, each fallback) and pluralising with the rules of the table the string came from. `setLocale` loads what the new chain needs (one pending promise per locale, the latest call wins) and then notifies `subscribe` callbacks, which is how a menu or HUD re-renders; `direction` is `'rtl'` for a small RTL language set and the store never touches the DOM. Numbers, dates, durations and lists go through cached `Intl` objects (`formatNumber`, `formatDate`, `formatDuration`, `formatList`). `negotiateLocale(available, requested = navigator.languages)` picks the table for a browser (exact, then language, then the fallback). Nothing in the engine imports `i18n`; `ui` may later. *Planned:* a `ui` binding that re-renders widgets from keys.

**Assets.** File formats become engine objects here, from bytes the game fetched (VISION rule 4: no network call in the engine). *Today:* glTF 2.0 geometry, skins and animations in `assets/`. `parseGltf(bytes | { json, buffers })` reads `.glb` and `.gltf` (data: URIs decoded, external URIs listed in `externalUris`) into an engine-free `GltfDocument`: per primitive position, normal (flat when absent), uv0, color0, indices (generated when absent) and bounds; per node TRS and 3×4 local and world matrices; per material base colour factor and texture, alpha mode and cutoff; per image bytes or uri. `loadGltf(renderer, doc, opts?)` makes one `Mesh` per primitive in `VERTEX_LAYOUT_3D` (with the primitive's bounds as `MeshDesc.bounds`, so `camera.cull` skips it), one `Transform` per node, one sRGB mipmapped `Texture` per image and one lit `Material` per glTF material (or the one `opts.material`), and the `GltfScene` draws them with `frame.mesh` per node without allocating. Sparse accessors outside morph targets, non-triangle modes and `extensionsRequired` throw `GltfError`. Skins and animations parse into the animation module's shapes without a converter: `doc.skins` (joints, 3×4 inverse bind rows), `doc.animations` as `AnimationClip`s (every interpolation, cubic-spline tangents kept), `primitive.joints`/`weights`, `interleaveSkinned` for the skinned vertex layout and `skeletonFromSkin` for a `Skeleton` with the rest pose from node TRS. Morph targets (ws/morph): `primitive.targets` (`POSITION` and `NORMAL` deltas per target, dense or sparse over zeros or a dense base; other target attributes listed in `ignoredTargetAttributes`) and `mesh.weights` parse; `loadGltf` keeps the base vertex buffer only for primitives with targets, blends them through `anim`'s `createMorphBlender` behind `scene.morph(nodeIndex)` (`GltfMorph`: one weights array per mesh, `apply()`), and `draw` uploads changed primitives with `Mesh.update`. A typed manifest (`defineManifest`) loads through `createBundle` from the game's `read(uri)` with bounded, prioritised, deduplicated reads, progress in assets and bytes, per-key errors, cancel and release, and `packAtlas` / `createAtlasTexture` shelf-pack sprites into one texture with extrusion and uv rects. Materials (ws/gltf-materials): the parser reads the whole metallic-roughness model with `KHR_texture_transform` and `KHR_materials_emissive_strength` (every slot a `TextureRef`, samplers, `TANGENT`, `TEXCOORD_1`), and `loadGltf` makes one standard PBR material per glTF material with one texture per (image, colour space), the file's sampler and transform, tangent-layout meshes for `TANGENT` primitives and skinned-layout ones bound to the game's `SkinPalette` (`opts.palette`). Extensions (ws/assets-3): quantized and meshopt-compressed meshes decode at parse time, `KHR_lights_punctual` lights and cameras reach `GltfScene.lights` / `cameras` as render records (a directional light as a `SunLight` whose `direction` is its node's world -Z, ws/assets-4), `KHR_materials_variants` switch materials in place through `scene.setVariant`, the remaining `KHR_materials_*` and KTX2 (`parseKtx2`) parse into data the renderer does not draw yet, and `createAssetCache` keeps loaded assets reference-counted under a byte budget. *Planned:* drawing the rest of `KHR_materials_*`, KTX2 upload.

**Analytics.** Typed, batched game events handed to a sink the game supplies; the engine makes no network call (VISION rule 4). *Today:* `createAnalytics<E>({ sink, session?, clock?, context?, onError?, maxBatch? })` in `analytics/` returns `emit(name, props)`, `flush()` and `attach(ctx)`. Each event carries `name`, `props`, a per-page-load `session`, a monotonic `seq` and `t`. `attach` emits `game_start` (form factor, host kind, DPR, viewport, embed, build), wraps `ctx.hooks.hide`, `show` and `deviceLost` (the game's hooks still run), emits `device_lost`, and on `hooks.hide(reason)` (hidden, pagehide, freeze) or device loss emits `session_end` with that reason and flushes; `show` re-arms it. It adds no lifecycle listeners of its own. A failing sink goes to `onError`; `emit` and `flush` never throw. `templates/puzzle` shows the conventions (ws/plumbing): a `navigator.sendBeacon` sink (`createBeaconSink(url)` in `templates/puzzle/src/analytics.ts`) and `level_start` / `level_complete` events.

**Geometry.** Shapes are arithmetic the game can call for, not files it must ship: a `Geometry` (`vertices`, `indices`, `bounds`, `layout`) is a `MeshDesc`, so `renderer.createMesh(geometry)` takes it as it is. *Today (ws/geom):* `@thunderclap-engine/engine/geom` (`geom/`) is pure TypeScript whose only `render/` imports are types. The builders `box`, `plane`, `sphere` (UV), `icosphere`, `capsule`, `cylinder` (and cones) and `torus` take sizes, segment counts, a `color` and a `uvScale`, and return `VERTEX_LAYOUT_3D` geometry wound counter-clockwise from outside with unit normals, flat where the surface is (box, plane, cylinder caps) and smooth where it is not; indices are 16-bit until a geometry passes 65535 vertices, then 32-bit. `Heightfield { width; depth; heights; scale; origin }` with `heightAt` (bilinear), `normalAt`, `raycastHeightfield` (a DDA over the cells the ray crosses, each cell's bilinear patch solved exactly, no allocation; the distance or -1) and `heightfieldGeometry` (smooth or flat). `mergeGeometry` concatenates parts and offsets their indices, `transformGeometry` applies a 3×4 world matrix to positions and its inverse transpose to normals, and `GeometryWriter` is the hand-built path the builders use. The second half (ws/geom-2) adds sweeps over a 2D `Profile2D` (`extrude` with bevelled ear-clipped caps, `lathe`, `sweep` and `tube` along a polyline with rotation-minimising frames, `polygon`, `stairs`, `arch`), `computeTangents` (MikkTSpace-style accumulation, orthonormalised, handedness in `w`) into `VERTEX_LAYOUT_3D_TANGENT` (the 3D layout plus `tangent: vec4f` at `@location(13)`, 16 floats), and the operations `flatShade`, `weld`, `flipWinding`, `projectUv`, `fitBounds` and `recenter`. Collision (ws/collide) lives in `geom/collide/`: `createStaticCollider` puts the triangles of placed geometry, heightfields and 2D tile grids under a BVH (one subtree per source, so a source can be refitted or removed; `exportCollider` bakes it), and `raycast`, `overlap`, `sweepShape` and the move-and-slide `slide` (ground within a slope limit, walls slid along, a step-up, a grounded probe and snap-down) answer for spheres, capsules and boxes, with `*2` variants lifting a circle or 2D box to the collider's height; every query is allocation-free, and what to do about a hit (forces, triggers, integration) is the game's. The third pass (ws/geom-3) adds the build-time pipeline: `cloneGeometry`, layout-driven `transformGeometry`/`mergeGeometry` (any layout with a position at float 0, normal and tangent lanes found by location), quadric-error `simplifyGeometry` and `createLodChain` with a pure `selectLod` by projected pixels (the renderer does not pick levels), `convexHull` and `collisionProxy`, `splitGeometry` and capped `sliceGeometry`, a positions-only collider source, and `slideTiles`, the y-down platformer box-vs-tiles slide with one-way tiles, step-up and carried movers.

**Part models.** A machine, creature or prop is data, not a file: a part tree whose shapes, turns and repeats `compileModel` packs into units (one static unit, one per moving or glowing top-level part) against a material code table the game declares, so the engine owns no material names. *Today (ws/models):* `@thunderclap-engine/engine/models` (`models/`). Motion (`spin`, `swing`, `hinge`, `slide`, `bob`) and glow read named state channels (at most four per model, each a value and a rate) and are evaluated in the vertex shader, so a turning sail costs no write per frame; `evaluateUnit` is the CPU twin for picking and tests. `ModelInstances` packs instances by slot with no GPU (writes only on place, a rebase every 600 s); `ModelScene` is a `Drawable` that uploads the dirty ranges and draws one call per unit in use; the style is the game's WGSL `model_shade(ModelSurface) -> ModelShaded` with `MODEL_MAT_*` constants generated from the table. Nested motion, facing rules and culling are left to the game (radii are kept for culling later).

**Scene and Ctx.** `Scene<Ctx, Frame, Cam>` and `SceneStack` are in `core/`. *Today:* `createGame(opts)` in `core/game.ts` (exported from the root entry `@thunderclap-engine/engine`, not `./core`, because it is the top layer and pulls in every module) builds the engine's ctx and resolves to `EngineCtx`, or to `null` when WebGPU is missing (the unsupported screen is shown). It blocks browser zoom (double-tap, pinch, ctrl+wheel; option `blockBrowserZoom`, default on), boots the letterboxed surface, and builds the renderer, post stack, particles, host, save (`opts.save(host)`, opt-in), overlay, pad nav, audio (with `persistMixer` when `mixerKey` is set), input (blocked under a modal) with its gestures (`new Gestures({ magnify: opts.input.magnify })`) and its pointer router (`createPointerRouter({ camera: () => xrSurface?.head ?? It wires resize (renderer, the overlay's frame via `ui.setFrame`, which re-lays the layout), the loop (frames from `host`; input → pad nav → `hooks.update` → particles → scenes, in fixed steps of `sim.step`, default 1/60; `hooks.beforeRender` → `renderer.beginFrame` → `stack.render(frame, ctx.camera, alpha)` → `renderer.render(frame, ctx.camera)` → `renderer.endFrame()` → `hooks.afterRender` → `ui.updateAnchors()`; while an XR session runs, the scenes record once through `xr.surface.head`, each eye renders into `xr.surface.scene` and `renderer.resolve` runs the post stack into the eye's part of the layer, and `endFrame({ present: false })` submits), page lifecycle (hidden, pagehide, freeze: stop the loop, `hooks.hide(reason)` with `HideReason` `'hidden' | 'pagehide' | 'freeze'`, flush the save; shown: resume the loop, then `hooks.show(reason)`, unless the device was lost) and device loss (boot shows the reload screen, then: halt the loop for good, `hooks.deviceLost`, halt audio, suspend the caption, flush).
